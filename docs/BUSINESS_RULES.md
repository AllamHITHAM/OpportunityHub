# OpportunityHub Business Rules

## 1. User Rules

- Every user must have one role: student, organization, or admin.
- User email must be unique.
- A suspended user cannot access protected features.
- Admin users manage platform approval and monitoring.

## 1a. Password Recovery & Email Verification Rules (Phase 8B-2)

- **Password recovery is a User-level concern, not a role-specific flow.** `POST /forgot-password` and `POST /reset-password` work identically for Student, Organization, and Admin accounts — there is exactly one recovery flow, not three.
- **The forgot-password response never reveals whether an email belongs to a real account.** The exact same response body/status is returned for a known email, an unknown email, and a throttled repeat request. This is the entire account-enumeration defense — no other special-casing exists or is needed.
- **No custom password-reset token system exists.** Token generation, hashing, storage (`password_reset_tokens`), the 60-minute expiry, and the 60-second per-email throttle are all Laravel's own untouched `Password` broker behavior (`config/auth.php`). The only backend customization is *where the emailed link points* (`AppServiceProvider::boot()`, via `ResetPassword::createUrlUsing()`) — never how the token itself is generated, hashed, or validated.
- **A reset token is single-use.** `Password::reset()` deletes the token row as part of a successful reset; the exact same token can never be replayed for a second reset.
- **Every existing Sanctum personal access token for the user is revoked when a password reset succeeds.** A session/device that was authenticated with the old password must not silently remain valid after the account owner (or someone who compromised the mailbox and is now recovering control) changes the password — the same reasoning `AuthController::logout()` already applies to a single token, extended here to *every* token for this account. A failed reset attempt (wrong/expired/reused token, validation failure) never touches any existing token.
- **The reset link points at the Flutter Web app, never a Laravel-rendered page.** `{FRONTEND_URL}/reset-password?token=...&email=...`, built from `config('app.frontend_url')` (the same `FRONTEND_URL` env var already used for every other outbound-email link — see the Phase 7A-4.1 email architecture in docs/ARCHITECTURE.md) — never a hardcoded host. Native mobile deep-link handling (opening this same link directly in the installed app instead of a browser) is explicitly deferred; Web is the supported v1 destination.
- **Email verification exists, but nothing is gated behind it.** `User implements MustVerifyEmail`; a verification email is queued at registration; `email_verified_at`/`email_verified` are real and meaningfully tracked. But `POST /register/*`, `POST /login`, and every existing protected route remain fully usable by an unverified account, exactly as before this phase — no route uses the `verified` middleware. This is a deliberate v1 decision (see the next rule), not an oversight.
- **Hard verification gating (e.g. blocking Student application submission or Organization opportunity creation until verified) is explicitly deferred, not implemented.** Adding it this close to submission carries real regression risk across already-completed, tested workflows for no corresponding urgent need — the infrastructure (verified status, resend, the signed link) is in place for a future phase to gate on if desired, but this phase does not make that call unilaterally.
- **The verification link is verified entirely by Laravel's own signed-URL mechanism** (`URL::temporarySignedRoute` / `$request->hasValidSignature()`), covering every route parameter including the target user's id — a link cannot be repointed at a different account by editing the URL, since doing so invalidates the cryptographic signature. No separate ownership/authentication check is needed or exists beyond this.
- **Verifying an already-verified email is safe and idempotent** — re-visiting a valid link a second time does nothing further (no error, no duplicate event, `email_verified_at` unchanged). Resending to an already-verified user is likewise a safe no-op (no email sent).
- **Password-reset and verification-resend endpoints are rate-limited** using Laravel's built-in `throttle` middleware only — no custom rate-limiter infrastructure. `forgot-password`/`reset-password`: 5 requests/minute (matching the existing `/login` convention). `verification-notification` resend and the verification link itself: 6 requests/minute.

## 2. Student Rules

- A student must have a user account before creating a student profile.
- A student can have only one student profile.
- A student can upload multiple CVs.
- A student can choose one CV when applying to an opportunity.
- A student can add multiple skills.
- A student cannot apply to the same opportunity more than once.
- A student can view their own applications and interview details only.
- **CV upload is a real multipart PDF upload (Phase 8A-4).** PDF only (`mimes:pdf`, checked against real file content, not just the extension), max 5 MB. The server generates a random filename for every upload — the client's original filename never determines where or under what name the file is stored, and a client can no longer supply an arbitrary `file_path` string at all. Files live in private storage (`storage/app/private/cvs/{student_id}/...`, the `local` disk), never the public web root — a CV file is only ever reachable through an authenticated, ownership-checked download endpoint (see docs/API.md section 4), never a direct/guessable URL.
- **Legacy CVs created before Phase 8A-4 may still have a non-managed `file_path`** (e.g. a plain string a student typed into the old text field, such as a local Windows path) — these rows are never migrated or deleted automatically; they simply behave as "file not found" (a controlled 404) if a download is attempted, and are left untouched by delete-time file cleanup (the backend only ever deletes a physical file it itself manages, under `cvs/{student_id}/...`).
- **Every newly-uploaded CV PDF has its plain text extracted deterministically, server-side, right after upload (Phase 8A-5)** — `App\Services\CvTextExtractor`, using the pure-PHP `smalot/pdfparser` library (no external executable, no shell-out, no OCR). The result is stored internally as `applications.cvs.parsed_text` (nullable `LONGTEXT`) purely as raw processing data for a **future** AI-matching phase — it is never exposed through any API response (Student or Organization), never used by `MatchingService`, and no skills/summary/explanation are derived from it in this phase. **This phase implements no AI/LLM call of any kind** — extraction is entirely mechanical (extract → normalize whitespace → store).
- **A scanned/image-only PDF is not OCR'd and is not rejected.** If a valid PDF simply has no extractable text layer, or (rarely) a PDF that already passed upload validation still can't be opened by the parser (corrupt structure, encrypted/password-protected), the upload still succeeds — `parsed_text` is simply left `null` in both cases. A CV is never rejected solely because its text isn't extractable.
- **CVs created before Phase 8A-5 (and any CV whose text genuinely isn't extractable) keep `parsed_text = null` — there is no automatic bulk backfill.** A future phase may add a manual/administrative re-parse action if this ever becomes necessary; none exists yet.

## 2a. Candidate Opportunity Preferences ("Interested In")

- **A Student declares which canonical Opportunity Type(s) they want to be recommended for** via `student_profiles.interested_in` — a JSON array of the exact same values `Opportunity.opportunity_type` uses (`job`, `internship`, `volunteer`, `scholarship`, `competition` — `App\Support\OpportunityType::ALL`, the single shared vocabulary both models validate against). Never a second, free-text, or independently-drifting vocabulary.
- **Multiple selections are allowed and expected.** A Student may genuinely want both Job and Internship opportunities, or Volunteer and Scholarship together — this is never forced down to one value.
- **Required whenever a Student actually sets it, never backfilled onto an existing profile.** `POST /api/student/profile` (initial Profile Setup) requires at least one entry (`required`, `min:1`); `PUT /api/student/profile` (Edit Profile) uses `sometimes`+`min:1` — omitting the key entirely leaves an existing selection untouched, but a present key can never be sent as an empty array (an Organization/Student cannot clear this preference down to zero, only replace it with a different non-empty set) — the identical convention `eligible_majors` already established for Opportunities. A profile created before this patch has `interested_in = null` and remains fully readable; nothing here breaks login, existing profile loading, or old Student accounts.
- **This preference gates Recommended Candidates only** (section 9's "Opportunity Type interest" rule) — it is never consulted by direct Apply or Invitation creation, and never changes those endpoints' existing rules. It also appears, purely informationally, on `GET /api/organization/candidates` (Talent Directory) rows — that endpoint is profile-browsing only and never itself filters by it.

## 3. Organization Rules

- An organization must have a user account before creating an organization profile.
- An organization can have only one organization profile.
- An organization must be approved by admin before publishing opportunities.
- An organization can create, update, and close its own opportunities.
- An organization cannot manage opportunities created by another organization.
- An organization can view applicants only for its own opportunities.
- An organization can update application status.
- An organization can schedule interviews for applications that are `shortlisted`, (legacy compatibility only) already `interview_scheduled`, or, **as of Phase 10A.3**, `in_assessment` with no currently-active Assessment (re-scheduling — and, as of Phase 10A.3, advancing a completed Quiz to a new Interview — is blocked separately by the active-Assessment-invariant rule, not by this status check). See section 7's "Assessment History & the Active-Assessment Invariant" for the full mechanism.

## 3a. Organization Public Profile & Company Updates Rules

- **An organization's public profile is only ever reachable once `approval_status = 'approved'`.** `GET /organizations/{id}` and `GET /organizations/{id}/posts` both 404 for a `pending` or `rejected` organization — the same gate `Public\OpportunityController` already applies to that organization's own Opportunities, so there is no way to browse a not-yet-approved organization's identity, description, or posts publicly.
- **The public profile is a deliberately narrow, explicit safe-field response** — `organization_name`, `organization_type`, `industry`, `description`, `website`, `phone`, and the canonical `location` (`{id, canonical_name}`, never a raw ID). `user_id` and `approval_status` (internal workflow state) are never included.
- **An organization can edit only its own profile**, via the pre-existing `PUT /organization/profile` (no new endpoint) — `organization_name`/`organization_type` required, `industry`/`description`/`website`/`phone`/`location_id` optional. `location_id` must reference a real row in the canonical Location Catalog (`locations`), never free text.
- **Company Updates ("Updates & Achievements") are simple, professional text posts — not a social-media feed.** No likes, comments, followers, shares, or reactions exist anywhere in this feature. Each post has an optional `title` and a required, non-blank `body`.
- **An organization may create, edit, and delete only its own posts.** `POST /organization/posts` requires the organization be `approved` (mirroring the same gate opportunity creation already has); `PUT`/`DELETE /organization/posts/{id}` do not require current approval (an organization later un-approved can still manage its own already-published content), but both still 404 for a post that isn't the authenticated organization's own — never a `403`, so a wrong-organization request can never confirm the post exists at all.
- **A Student (or any other role) can only ever read posts, never create/edit/delete one.** Reading is the same public endpoint the owner's own Company Profile screen reuses (`GET /organizations/{id}/posts`), newest first.
- **Deleting a post never affects the organization's profile, opportunities, or any recruitment data** (Application/Invitation/Assessment/Offer), and deleting an organization's profile cascades to delete its own posts only (`organization_posts.organization_id` is `cascadeOnDelete()`), never another organization's data.
- **"Open Opportunities" on a Company Profile reuses the existing public Opportunity list** (`GET /opportunities?organization_id={id}`) — the same open-and-approved-only query every other public Opportunity browsing already uses, never a second eligibility/visibility rule.
- **Company Profile Polish phase — a closed Opportunity may be permanently deleted only when it belongs to the authenticated Organization, is genuinely `status = 'closed'`, and has no recruitment history to preserve** (no Application, no Invitation, no authored shared Quiz Template — see section 4's own deletion rule below for the full dependency list). This is enforced server-side by a dedicated `DELETE /organization/opportunities/{opportunity}/closed` endpoint, never by Flutter hiding a button; a wrong-organization, non-closed, or has-history request is always rejected regardless of what any client sends.
- **A Company Logo and a post image are both optional, single, real uploaded images — never a gallery, never a fabricated placeholder.** Standard web-safe raster formats only (jpg/jpeg/png/webp), real image-data validated (not just filename/MIME), capped at 2MB, server-generated random filenames (never the client's filename), served from the `public` disk as a full URL — the raw storage path is never exposed to a client. Missing either is always represented as `null` (`logo_url`/`image_url`), never a fake stock image.

## 4. Opportunity Rules

- Every opportunity belongs to one organization.
- Opportunities can be job, internship, volunteer, scholarship, or competition.
- Opportunities can be open, closed, or draft.
- Closed opportunities cannot receive new applications.
- **An Opportunity is genuinely open for applications only when `status = 'open'` AND (`application_deadline` is null, OR that deadline has not yet passed) — Final Company Profile Manual-E2E Bug Fix.** `application_deadline` is date-only, compared as a whole calendar day, never a raw timestamp: the deadline's own day still counts as open through all 24 hours (end-of-day semantics), and only the day *after* it is genuinely expired. Backend server time is authoritative; no client/request timezone is ever consulted. This single rule (`Opportunity::hasDeadlinePassed()`/`isOpenForApplications()`/`scopeOpenForApplications()`) is reused everywhere "is this open" matters — public discovery/details (real-time, independent of whether the row's persisted `status` has caught up yet), Student application submission (rejects an expired deadline with a 422, regardless of scheduler timing), and the auto-close sweep below — never a second, slightly-different date comparison duplicated in any one of them.
- **A `status = 'open'` Opportunity whose deadline has passed is automatically, persistently transitioned to `status = 'closed'` (Final Company Profile Manual-E2E Bug Fix).** `OpportunityExpirationService::closeExpired()` does this — idempotent, never touches `draft`, never touches an Opportunity with no deadline (stays open indefinitely), never deletes or modifies any Application/Invitation/Assessment/Quiz/QuizAttempt/Interview/Offer/Notification. Runs from two places: lazily, at the top of every `Organization\OpportunityController` read (so an organization's own dashboard is always accurate the moment it's opened, with zero dependency on a scheduler), and a daily scheduled `opportunities:close-expired` command (background consistency for an organization that never logs back in) — the lazy path is what makes correctness never depend on the scheduler actually having run.
- **`closed_at` is the real, authoritative moment an Opportunity became closed (Closed Opportunities Scalability Polish) — never `updated_at`, which changes for any unrelated edit.** Set to the real current backend timestamp (`now()`, never backdated) whenever `status` transitions TO `closed` — both a manual close (`PUT /organization/opportunities/{opportunity}` with `status: closed`) and automatic expiration closure. Cleared back to `null` on a genuine reopen (`status` transitioning away from `closed` — the pre-existing generic Edit Opportunity form has always allowed freely changing `status`; this phase doesn't invent reopening, only makes its `closed_at` bookkeeping correct). Re-saving an already-`closed` Opportunity (status unchanged) never bumps `closed_at`. A **legacy** closed row from before this column existed has `closed_at = null` UNLESS its `application_deadline` had already passed at migration time, in which case a one-time, deterministic backfill set it to that deadline's own expiry boundary (`deadline + 1 day`, start of day) — the earliest moment that specific row is provably known to have become closed. Every other legacy closed row (no deadline, or a deadline that hadn't passed — meaning it was closed manually, before its own natural expiry) has no reliable signal for its true closure time and is deliberately left `null` rather than a guess; the UI shows "Closure date unavailable" for that case, never a fabricated date.
- **An Opportunity can be permanently deleted only when it has no recruitment history (Company Profile Polish phase).** `hasRecruitmentHistory()` checks Applications, Invitations, and an authored shared Quiz Template (Phase 10A.4B) — all three currently `cascadeOnDelete()`, so this check is what actually prevents them from silently disappearing. A Conversation (Messaging MVP) existing does NOT block deletion — `conversations.opportunity_id` is `nullOnDelete()` by that feature's own design, preserving message history regardless. The pre-existing generic delete endpoint enforces this for any status (`draft`/`open`/`closed`); a separate, closed-only endpoint additionally requires `status = 'closed'` for the Company Profile's own cleanup action — see section 3a.
- Each opportunity can have multiple required or preferred skills.
- Required skills have higher priority in AI matching than preferred skills.
- **An opportunity can accept more than one major (Phase 8B-3.2).** `eligible_majors` is an explicit, ordered list of plain major names stored in a dedicated `opportunity_eligible_majors` table (e.g. a "Software Developer Internship" may accept Computer Engineering, Computer Science, and Software Engineering). See section 5b for the exact eligibility rule this list feeds into.
- **`field_of_study` is deprecated/legacy metadata (Opportunity Academic Matching Cleanup) — `eligible_majors` is the sole canonical academic-eligibility source.** The single free-text `opportunities.field_of_study` column still exists and is preserved unmodified for every historical Opportunity (the column is deliberately not dropped), but new Create/Edit Opportunity requests from Flutter no longer send it, it is never read by `MatchingService`/`OpportunityEligibilityService` or shown anywhere in the Organization-facing Opportunity UI, and it is never part of any Match explanation. See section 5b and section 9 for the two rules this closes (it was never an eligibility input, and as of v1.2 it is no longer a scoring input either).
- **An opportunity declares its own recruitment process (Phase 10A.4B).** `recruitment_process` is one of `none` (the column's own default — the pre-10A.4B unrestricted ad-hoc "Choose Assessment" flow, Interview or a private Quiz freely chosen per candidate), `interview` (candidates go straight to Interview), or `quiz` (candidates are advanced to this Opportunity's own shared Quiz template — see section 7a's "Shared Quiz Template"). Deliberately 3 values, not 4 — see that subsection for why a decision-free "Quiz Only" mode doesn't structurally exist once Phase 10A.4A made a real Organization decision mandatory before any Quiz result can reach a Student. Optional on both create and update (`sometimes`, not `required`) for backward compatibility — every existing Opportunity, and every existing caller that doesn't send it, keeps working exactly as before.
- **An opportunity's location is a canonical Location Catalog reference (Phase O8.2), never free text.** `location_id` (nullable) replaces client-supplied free-text `location` going forward — see section 5c for the full canonical-location model and the eligibility rule it feeds into. The legacy `location` string column is preserved for historical rows and mirrored automatically from the chosen Location's name whenever `location_id` is set, so nothing that already reads `location` needed to change.
- **Required/Preferred Skills are selected from the canonical Skill Catalog by ID only (Phase O8.2 reaffirms an existing rule)** — `opportunity_skills.skill_id` has always referenced `skills.id`; there has never been a free-text Skill name on an Opportunity. What's new in Phase O8.2 is a one-call sync endpoint (`PUT /organization/opportunities/{opportunity}/skills`, see docs/API.md) so Create/Edit Opportunity's Required Skills multi-select can save its whole selection atomically, and an Organization-side mirror of the Skill Catalog (`GET /organization/skills/catalog`) so that multi-select offers the same canonical IDs a Student's own skill list uses. Recommended Candidates ranking continues to reuse the one existing `MatchingService` formula — this phase never introduces a second, competing scoring system.

## 5. Application Rules

- Every application belongs to one student and one opportunity.
- Every application must use one CV.
- Application status can be:
  - pending
  - reviewed
  - shortlisted
  - in_assessment
  - offer_sent
  - interview_scheduled *(deprecated — legacy compatibility only, see below)*
  - accepted
  - rejected
  - withdrawn
- Match score is calculated after application submission.
- **As of Phase 6C-0, `accepted` means specifically "the student accepted the Offer."** It is no longer organization-writable through the generic status endpoint — the only workflow permitted to set it is `Student\OfferController::accept()` (`App\Services\OfferService::acceptOffer()`, Phase 6C-1 — see section 7b). Pre-existing `accepted` rows from before Phase 6C-0 are untouched and remain fully valid, legacy-compatible data; the semantics shift only governs writes going forward.
- `rejected` continues to mean the hiring process ended negatively — either the organization declined the candidate directly at any appropriate stage before an Offer exists (section 3, section 7), or the student declined a sent Offer (`Student\OfferController::decline()`, section 7b). Both converge on the same `Application.status = rejected`; only the actor and, for the Offer case, `Offer.status = declined` distinguish which happened — see section 7b. **It remains directly organization-writable through the generic status endpoint only up until an Offer exists for the application** — as of Phase 6C-4, once an Offer exists (`sent`, `accepted`, or `declined`), the generic endpoint is blocked entirely (`409`), even for `rejected`; see the Offer integrity rule below and section 7b. A rejected application is not automatically re-openable — reversing one requires a manual data change, not an API action; this is a stated rule, not one enforced by the API.
- **Offer/Application integrity rule (Phase 6C-4): once an Offer exists for an application, `Application` and `Offer` lifecycle are synchronized and the generic `PUT /api/organization/applications/{application}/status` endpoint can no longer independently override that lifecycle — for any requested status, not `rejected` alone.** Without this, an organization could otherwise reject an application whose Offer is still `sent`, producing the impossible combination `Offer.status = sent` + `Application.status = rejected`. v1 has no Offer cancel/rescind workflow (section 7b), so this is an unconditional block, not a conditional one, enforced in `Organization\ApplicationController::updateStatus()` with a `409` (`"This application already has an offer; its status can only change through the offer accept/decline endpoints."`). The student's accept/decline response (section 7b) remains the only way an application with a `sent` Offer can move again.
- A withdrawn application is controlled by the student; once `withdrawn`, no further status change is accepted from any source (`409`).
- **`application.status` owns recruitment progress only** (Phase 4A-1 decision, reaffirmed by Phase 6B-0 and Phase 6C-0/6C-1). It does not, and must not, describe assessment-path/assessment-outcome detail (that belongs to `assessment.status`/`assessment.result`, see section 7) or Offer-specific detail (that belongs to `offer.status`, see section 7b) — it only ever tracks the overall stage the application itself is at.
- **`in_assessment` (Phase 6B-0) is the generic application-level status meaning "an evaluation chain exists for this application and is not yet finalized into an Offer/Reject."** It is written by `AssessmentService::transitionToInAssessment()` whenever a real `Assessment` is created — for both `type=interview` and `type=quiz`, without introducing a second status per type. **As of Phase 10A.3**, this can happen more than once for the same application ("Advance to Interview" writes it again after a completed Quiz) — each write is a safe no-op in that case, since the application is already at `in_assessment`; this deliberately does **not** encode "quiz then interview" as its own status (see section 7's "Assessment History & the Active-Assessment Invariant"). It can never be set directly through the generic `PUT /api/organization/applications/{application}/status` endpoint — it must always be the byproduct of a real Assessment-creation workflow (see section 7 and docs/API.md section 5).
- **`offer_sent` is the generic application-level status meaning "the organization has sent a final Offer, and the student's response is pending."** It is written from exactly one place — `OfferService::sendOffer()` (Phase 6C-1, section 7b) — whenever an `in_assessment` application with a completed Assessment receives an Offer. Like `in_assessment`, it can never be set directly through the generic status endpoint.
- **`interview_scheduled` is deprecated, legacy-compatibility-only.** Before Phase 6B-0, assessment creation wrote this value instead of a generic one; it remains a valid, readable `application.status` for pre-existing records (and is still an accepted *source* status for creating an assessment, so an old application stuck at `interview_scheduled` with no real Assessment can still receive one — see section 7). It can no longer be set through the generic status endpoint, and no code path writes it going forward — new Assessment creation always writes `in_assessment` instead. It is also never treated as equivalent to `in_assessment` for Offer eligibility — see section 7b.
- **The generic organization status endpoint may set only `reviewed`, `shortlisted`, or `rejected`.** As of Phase 6C-0 it can no longer set `accepted` (see above) — combined with the pre-existing exclusions of `in_assessment`, `offer_sent`, and `interview_scheduled`, this endpoint is now purely for early-funnel screening moves and rejection; every other transition is the byproduct of a real domain workflow (Assessment creation, section 7; the Offer workflow, section 7b).
- **Responsibility boundaries across the assessment/offer stack** (Phase 6B-0, extended Phase 6C-0/6C-1): `Application.status` owns recruitment progress and the two generic "a workflow is active" signals (`in_assessment`, `offer_sent`); `Assessment.type` identifies which kind of evaluation is active (`interview`/`quiz`); `Assessment.status`/`Assessment.result` own the generic evaluation lifecycle/outcome shared by every assessment type; `Interview.status`/`Quiz.status` own their own type-specific state; `Offer.status` (`sent`/`accepted`/`declined`, section 7b) owns Offer-specific state the same way, without `Application.status` ever needing more than its own two generic signals plus the final `accepted`/`rejected` outcome.

## 5a. Candidate Search & Invitation Rules (Phase 8B-3)

- OpportunityHub supports two application-entry paths. **Flow A** (unchanged): Student browses → applies → Organization reviews → shortlist/reject → assessment → offer. **Flow B**: Organization searches Students → selects one → selects one of its own Opportunities → sends an Invitation to apply → Student accepts or declines. Both flows converge into the exact same `Application` pipeline the instant an `Application` exists — see docs/ARCHITECTURE.md.
- **The Organization can never force an Application into existence.** Sending an invitation only ever creates an `Invitation` row. An Application is created only through the existing Student-driven Apply endpoint (`POST /api/opportunities/{opportunity}/apply`), which the Student must complete themselves — even after accepting an invitation.
- **Candidate Search is filter/search-only.** No semantic search, no embeddings, no AI ranking, and no `MatchingService` call — a match score is only ever meaningful once a real `Application` exists for a specific Opportunity. Only Students whose `user.status = 'active'` are discoverable. Returned fields are deliberately narrow: name, university, major, graduation year, education-verification status, and skills (name + evidence source). Email, phone, bio, profile image, raw CV text, and any education-verification document path are never included.
- An Organization may only invite to **its own** Opportunity, and only while that Opportunity's `status = 'open'`. Inviting to another organization's Opportunity, or a `draft`/`closed` one, is rejected.
- **Duplicate/conflict rules**, checked in order: a Student who already applied to the Opportunity cannot be invited to it (`409`). A single `unique(opportunity_id, student_id)` database constraint on `invitations` then blocks any second invitation for that same Student/Opportunity pair, in any status — a second pending invite, a re-invite after acceptance, and a re-invite after a decline are all rejected the same way (`409`). This is the simplest non-duplicating rule available: one invitation per Student per Opportunity, for its entire lifetime.
- **Accepting an invitation never creates an Application.** `applications.cv_id` is a required column and no CV is chosen at invitation time, so inventing an Application here would mean either guessing a CV on the Student's behalf or inserting an invalid row — neither is acceptable. Accepting only flips `Invitation.status` to `accepted`; Flutter then routes the Student to the existing Opportunity details/Apply screen, where they pick a CV exactly as a direct (Flow A) applicant would. If the Student already applied independently before responding, accepting still succeeds — it only records consent, and no second Application is attempted.
- **Declining an invitation never creates an Application and never triggers a `match_score` calculation.** `Invitation.status` flips to `declined` and nothing else happens.
- An invitation's `status` (`pending` → `accepted`/`declined`) can only ever be set once by the receiving Student — a repeated accept/decline attempt is rejected (`409`, "This invitation has already been responded to"), and an Invitation belonging to a different Student is a controlled `404` ("Invitation not found"), never a 403 that would confirm it exists.
- **Once an Application exists** (through either flow), it is a completely ordinary Application: `MatchingService` calculates and stores its `match_score` automatically, it appears in the Organization's normal ranked applicant list (section 5), and the full shortlist/reject/assessment/offer workflow applies identically. There is no second recruitment pipeline for Flow B.
- Education-verification status may be shown in Candidate Search results, but **verification is never a prerequisite for sending or accepting an invitation** in this phase.

## 5a-i. Talent Directory vs. Opportunity Recommended Candidates (Phase O8.1)

- **Problem this closes**: before this phase, "Find Candidates" conflated two different jobs — general profile discovery, and figuring out who to invite to a *specific* Opportunity — behind one screen and one endpoint, with no ranking and an Invite flow that made the Organization pick the Opportunity manually every time, after already having narrowed to one candidate.
- **Talent Directory** (`GET /api/organization/candidates`, section 5a) stays exactly what Candidate Search always was: general profile browsing, filter/search-only, no ranking. Its UI purpose narrows to pure discovery — the Organization can view a Student's profile, but inviting is no longer initiated from this screen.
- **Opportunity Recommended Candidates** (`GET /api/organization/opportunities/{opportunity}/recommended-candidates`, section 5a) is new: given one specific, already-known Opportunity, it proactively ranks the real, eligible Students by real match score, highest first, and is the one place Inviting happens with the Opportunity context already fixed (no second "choose an Opportunity" step).
- **The match score shown here is computed by the exact same `MatchingService` formula an `Application`'s own Match Analysis uses (section 9)** — extracted into `MatchingService::score(StudentProfile, Opportunity)` / `scoreCandidate()` so both call paths share one implementation. **This computation never creates an `Application`, a temporary/placeholder row, or any other persisted side effect** — it is a pure, read-only calculation over the Student and Opportunity that already exist. There is no second, competing scoring algorithm. See section 9 for the exact formula, and section 9's "Why not 100%?" note for `match_breakdown`, the deterministic explanation object built from that same formula's real intermediate values.
- **Eligibility is applied before ranking, on three independent axes, all via `OpportunityEligibilityService`**: Opportunity Type interest (`isTypeInterestEligible()`, section 2a — Recommendation-only, mirrors Location's own scoping), canonical Major (`isStudentEligible()`, the same gate as section 5b), and canonical Location (`isLocationEligible()`, section 5c). A Student who fails any one of the three is filtered out entirely, never shown with a low score. Recommended Candidates never returns a Student who could not actually be invited.
- **The Organization still chooses who to invite.** This endpoint ranks and surfaces candidates; it never auto-invites, auto-shortlists, or bulk-invites on its own. Every invitation sent from this screen goes through the same `POST /api/organization/invitations` endpoint and the same duplicate/eligibility/ownership rules as always (section 5a).
- **Applied/Invited state shown here is always the real, current relationship** for that specific Student/Opportunity pair (`already_applied` + `application_id`, or `invitation_status`) — never fabricated, and this endpoint never mutates either. A Student who already applied is shown "Applied" with a link to the real Application, not an Invite action the backend would reject anyway.
- **Privacy is unchanged from Candidate Search**: never phone, email, bio, raw CV text, or education-verification document path, and an Organization can only ever request recommendations for its own Opportunity (404 otherwise) — see section 5a-ii below.

## 5a-ii. Recommended Candidates Access Control (Phase O8.1)

- **Ownership is strictly enforced**: an Organization may only request recommendations for an Opportunity it owns. A request for another organization's Opportunity — even a valid Opportunity ID — returns `404` ("Opportunity not found"), the same convention already used everywhere else an Organization-scoped resource is addressed by ID (never a `403` that would confirm the Opportunity exists for someone else).
- **Students cannot reach this endpoint at all** — it sits behind the same `role:organization` middleware group as the rest of section 5a; a Student request is rejected before any Opportunity lookup happens.
- **No new private data is exposed.** The same narrow field set as Candidate Search, plus only the derived `match_score`/factor scores, `match_breakdown` (a truthful re-labeling of those same scores — see section 9), and this-Opportunity relationship state — never a private CV file the Organization isn't already authorized to see, correct Quiz answers, a Student's other Applications, another Assessment's private data, or another Organization's interactions with this Student.

## 5b. Multi-Major Opportunity Eligibility Rules (Phase 8B-3.2)

- **Problem this closes**: before this phase, an Organization could invite (or a Student could apply to) any active Student regardless of whether their major/field was appropriate for the Opportunity, and an Opportunity could only ever declare one major via the legacy free-text `field_of_study`.
- **The Student eligibility rule** — implemented once in `App\Services\OpportunityEligibilityService::isStudentEligible()` and reused everywhere it is enforced (never duplicated):
  - **(A)** If the Opportunity has an explicit, non-empty `eligible_majors` list (section 4), the Student's `StudentProfile.major` is eligible only if it normalize-matches **any one** of those majors.
  - **(B)** Else (the Opportunity has no explicit `eligible_majors`), the Opportunity is unrestricted — every Student is eligible regardless of major, including one with no major set at all. `field_of_study` is **never** consulted here — it is descriptive metadata about the Opportunity (what field it relates to), not an eligibility restriction. An Opportunity with `field_of_study = "Computer Engineering"` and an empty `eligible_majors` list is open to every major, exactly as if `field_of_study` were blank.
  - A blank/null Student major can only ever satisfy rule (B); it can never match under (A).
- **Normalization** (`App\Support\MajorNormalizer`, mirrors the pre-existing `SkillNameNormalizer`): trim, collapse internal whitespace to a single space, lowercase. `"Civil Engineering"`, `"civil engineering"`, and `"  Civil   Engineering "` are all the same major for eligibility purposes. This is deliberately simple string normalization — there is no fuzzy/semantic matching and no major-name catalog/synonym table in this phase.
- **This eligibility gate is checked before, and independently of, `match_score`** — it decides "is this Student allowed to become an applicant for this Opportunity," never "how good a fit are they," and it never consults Skills or the score. **As of "Recommendation Match: Major Must Contribute to Total Score" (v1.3), this same canonical `eligible_majors` comparison is *also* genuinely scored** as `MatchingService::analyzeMajor()` (section 9, 20% weight) — the gate and the score factor are two separately-computed things that happen to agree for any candidate reached through the normal path (see section 9 for the full "why" and why this deliberate overlap is not the double-counting the Opportunity Academic Matching Cleanup originally ruled out). `eligible_majors` remains the sole academic *data source* everywhere in the system, for both eligibility and scoring — `field_of_study` is never consulted for either.
- **Where the rule is enforced** (all backend-authoritative — Flutter may hint at eligibility in its UI, but the API re-validates independently and cannot be bypassed by calling the API directly):
  - **Opportunity-scoped Candidate Search** (`GET /api/organization/candidates?opportunity_id=...`, section 5a): results are filtered to only Students eligible for that Opportunity. The general search (no `opportunity_id`) is completely unaffected and still returns every active Student profile — this rule only ever narrows an Opportunity-scoped search.
  - **Recommended Candidates** (`GET /api/organization/opportunities/{opportunity}/recommended-candidates`, section 5a-i): the same filter, applied before ranking — an ineligible Student never appears, regardless of what their match score would have been.
  - **Sending an Invitation** (`POST /api/organization/invitations`, section 5a): rejected with `422` ("Student major is not eligible for this opportunity") if the target Student is not eligible for the target Opportunity. This check is a real backend guard, not client-side filtering only.
  - **Direct Student Apply** (`POST /api/opportunities/{opportunity}/apply`, section 5): also rejected with `422` ("Your major is not eligible for this opportunity") under the identical rule. This was a deliberate consistency decision: without it, Invitation would block an ineligible Student while direct Apply still let the same Student in through the front door, defeating the point of the guard. Both entry points call the same `OpportunityEligibilityService` — the rule is defined once, never re-implemented per controller.
- **`eligible_majors` is now required on Opportunity create (Opportunity Requirements Integrity Patch — supersedes the original "optional" decision above)**: at least one entry is mandatory to create a new Opportunity, and an *existing* set may be left untouched on update but never explicitly cleared to empty. `field_of_study` remains separately optional and purely descriptive — it is still never consulted for eligibility (rule B above is unchanged; it simply can no longer be reached by a brand-new Opportunity, since one must always declare `eligible_majors` now). A historical Opportunity created before this patch with zero `eligible_majors` remains fully readable/editable; the requirement only engages the moment the Organization actually sends `eligible_majors` on an update. Required Skills follow the identical rule — see section 5b-i below.
- **Existing Invitations are never retroactively affected.** This rule only gates the creation of new Invitations and new Applications going forward; pending/accepted/declined Invitations created before this phase remain exactly as they were.

## 5b-i. Required Skills on Opportunity Create/Update (Opportunity Requirements Integrity Patch)

- **Problem this closes**: Required/Preferred Skills (`opportunity_skills`, real canonical `skills.id` references) could previously be added to an Opportunity only *after* creation, via a separate `PUT /organization/opportunities/{opportunity}/skills` call — meaning a new Opportunity could be created and left with zero Required Skills indefinitely, and Recommended Candidates' own Skills factor (section 9) had nothing real to score against for it.
- **At least one Skill entry (`skills: [{skill_id, is_required}]`) is now required on Opportunity create**, validated against the real canonical Skill Catalog (`exists:skills,id`) — the identical `min:1`-when-present rule `eligible_majors` follows (5b above). Skills are saved **atomically** with the Opportunity itself and its `eligible_majors`, in the same database transaction — `OpportunitySkillSyncService` is the one shared implementation both `OpportunityController::store()`/`update()` and the standalone `PUT .../skills` endpoint call, so there is never a second, drifting sync algorithm and never a window where an Opportunity exists with a validation-required field silently missing.
- **On update**, `skills` may be omitted (leaves the existing set untouched) but, like `eligible_majors`, may never be sent as an explicitly empty array once the key is present — an Organization cannot clear an Opportunity's Skills down to zero, only replace them with a different non-empty set.
- **A historical Opportunity created before this patch with zero Required Skills remains fully readable and editable** for every other field; the requirement only engages the moment the Organization actually sends `skills` on an update.
- **The exact same `opportunity_skills` relation powers both Opportunity Details' "Required Skills" display and Recommended Candidates' Skills factor/`match_breakdown`** (section 9) — there is one canonical source of truth for what an Opportunity's Required Skills are, never two.

## 5c. Canonical Location Catalog & Location Eligibility Rules (Phase O8.2)

- **Problem this closes**: before this phase, "location" existed only as a free-text string per Student profile field and per Opportunity — meaning "Nablus", "Nablus, Palestine", "نابلس", and "Nablus City" could never reliably be recognized as the same place, and nothing enforced location relevance to eligibility at all.
- **Canonical model**: a new `locations` table (`id`, `canonical_name`, unique) is the single source of truth for real places — a fixed, admin-curated catalog. Every reference to a location anywhere in this app — a Student's available work locations, an Opportunity's own location — goes through a `location_id` (or a pivot row keyed on one), never a raw display string. The ambiguity in the problem above is removed by construction (there is no free-text location input left anywhere in this flow), not fixed after the fact with fuzzy string matching.
- **A Student has two deliberately distinct location facts, never conflated (Student Location Profile Patch):**
  - **Current Location** (`student_profiles.current_location_id`, nullable, single) — where the Student lives. Purely informational; never consulted by `isLocationEligible()` or any other eligibility/ranking logic.
  - **Available Work Locations** (`student_available_locations`, a many-to-many pivot, multiple) — where the Student is willing to work. This, not Current Location, is what On-site/Hybrid location eligibility actually checks.
  - A Student may live in Jenin but be willing to work in Nablus and Ramallah — both facts are real, both are stored, and setting one never touches the other. Both are a completely valid, truthful empty state for a Student who hasn't configured them yet, never an error. Managed via `PUT /api/student/profile`'s `current_location_id` and `available_location_ids` respectively (see docs/API.md), settable at Student Profile Setup (registration) and again later via Edit Profile — never on the minimal Step 1 account form.
- **An Opportunity references at most one canonical location** (`opportunities.location_id`, nullable). The legacy free-text `opportunities.location` column is preserved unmodified for every historical row and mirrored automatically from the chosen Location's `canonical_name` whenever a new/edited Opportunity sets `location_id` — see section 4. `location_id` is not required even for an On-site/Hybrid Opportunity, for the same "don't add a new stricter requirement" reasoning `eligible_majors` already established.
- **Work Mode controls whether location is relevant to eligibility at all** — implemented once in `App\Services\OpportunityEligibilityService::isLocationEligible()`:
  - **Remote**: location is never consulted. Never awarded or removed points, never used to filter, regardless of what either party's location data says.
  - **On-site or Hybrid, and the Opportunity has a real `location_id`**: a Student is eligible only if that ID appears in their own `available_location_ids`.
  - **On-site or Hybrid, but the Opportunity has no `location_id` set** (a historical Opportunity, or one an Organization hasn't configured yet): treated as unrestricted, mirroring rule B of the major-eligibility rule (section 5b) — there is nothing to compare against, so nobody is excluded on location.
  - **Missing Student location data is never guessed.** A Student with zero configured available locations is excluded from an On-site/Hybrid Opportunity's ranked recommendations — the truthful "cannot confirm eligibility" answer — never inferred from university location, phone number, or any other unrelated data, and never assumed eligible either.
- **Existing Students remain fully valid with no location data at all.** Both `current_location_id` and every `student_available_locations` row are purely additive — an account that existed before this patch shipped simply has `current_location = null` and `available_locations = []`, and continues to log in, load its profile, and use every other feature exactly as before. This is never treated as an error and never triggers an automatic/guessed default; it only ever surfaces as a truthful "not added yet" state in the UI (Profile Readiness, Work Preferences display) until the Student configures it via Edit Profile.
- **Location eligibility is a filter, not a scoring factor.** It is never awarded or subtracted as a percentage inside `MatchingService`'s `match_score` — a candidate either passes the filter and is ranked by the real, existing match formula, or is excluded from the list entirely. This mirrors how major eligibility (section 5b) is also a pre-ranking gate, never a `match_score` input.
- **Deliberately scoped to Recommended Candidates only — not Apply or Invitation creation.** Unlike major eligibility, `isLocationEligible()` is a separate method from `isStudentEligible()` and is called only by `Organization\OpportunityRecommendationController`. Every existing Student profile has zero `available_location_ids` the moment this field ships, and folding location into the same gate that already blocks Apply/Invitation would have immediately made every one of them unable to apply to or be invited to any On-site/Hybrid Opportunity until they filled in a brand-new field — a much larger, retroactive behavior change than this phase asked for. Being excluded from a *recommendation* list carries no such risk: the Student can still be found via Candidate Search or apply directly. This is a deliberate scope decision, not an oversight — flagged here so a future phase can revisit it deliberately if location-gated Apply/Invitation is ever wanted.
- **Recommendation Page transparency (Phase O8.2)**: the Recommended Candidates screen shows a truthful, professional explanation of what the list actually is — real candidates already filtered against the Opportunity's configured eligibility (majors, and location where Work Mode requires it) and then ranked by match, never random profiles. The explanatory copy is adapted to the real Opportunity configuration: it never mentions location matching for a Remote Opportunity, and never mentions it for an On-site/Hybrid Opportunity with no canonical location configured either (nothing was actually filtered on location in either case) — see `GET .../recommended-candidates`'s `data.opportunity.work_mode`/`location` in docs/API.md, which is exactly what the UI reads to decide this truthfully rather than guessing from context.

## 6. Interview Rules

- Every interview belongs to one **assessment** (Phase 4A-1) rather than directly to an application — an interview is reached via `application → assessment → interview`. An assessment can have at most one interview (enforced by `interviews.assessment_id` being unique). **Before Phase 10A.3**, this meant an application could also, in effect, have at most one interview, because it could have at most one assessment, ever. **As of Phase 10A.3**, an application can accumulate multiple Interview-type assessments over its lifetime (e.g. a completed Quiz followed by a real Interview — "Advance to Interview"; in principle, even two sequential Interview assessments) — see section 7's "Assessment History & the Active-Assessment Invariant". `Application::interview()` (a read-only convenience accessor) always resolves to the *most recent* one, deterministically.
- Interviews can be online, phone, or on-site.
- Interview details must include date and time.
- **Interview type determines the required attendance detail (Phase Final-QA-1): phone -> `contact_phone`, online -> `meeting_link`, onsite -> `location`.** Exactly one is required, matching `interview_type`; the other two are never required and, if sent anyway, are cleared rather than stored — see "Stale-data safety" below. `meeting_link` must additionally be a real `http`/`https` URL, not just any non-blank string. This closes a prior gap where, for example, a Phone interview could be scheduled with no contact number at all, leaving the Student with no way to know how to attend.
- **Legacy rows may lack the detail (Phase Final-QA-1).** Interviews scheduled before this phase can have a null `contact_phone`/`meeting_link`/`location` even where their `interview_type` would now require one — existing rows are never invalidated or backfilled. The new requirement applies only to interviews scheduled or edited from this phase onward. A missing value on a legacy row is displayed as "Not specified" in Flutter rather than causing an error.
- **Stale-data safety on interview type change (Phase Final-QA-1).** If an already-scheduled interview's `interview_type` changes (e.g. phone -> online), the now-irrelevant old detail is cleared at the same time — a Phone interview's `contact_phone` does not linger once it becomes an Online interview. This applies to every write path (create and update), enforced once in `App\Support\InterviewContactDetailNormalizer`, never per-controller.
- Each interview can record a decision (pending, passed, failed, waiting) and an optional rating after it is completed. Completing an interview also updates its assessment's `status`/`result`/`completed_at`, but never changes the application's status — that remains a separate, organization-triggered decision.
- All existing Interview API routes (`/api/organization/applications/{application}/interview`, `/api/organization/interviews*`, `/api/student/interviews`) continue to work exactly as before; this phase is a backend restructuring, not a behavior change to any of them (see docs/API.md section 6).

## 7. Assessment Rules

Added in Phase 4A-1 as the shared foundation for the Interview/Quiz assessment paths; Phase 4A-2 adds the ability to create an interview assessment generically; Phase 6B-1 adds real Quiz creation and organization authoring; Phase 10A.3 adds Assessment *history* (below).

- An assessment belongs to one application; **as of Phase 10A.3, an application may have more than one assessment over its lifetime** — see "Assessment History & the Active-Assessment Invariant" below. Before Phase 10A.3, `assessments.application_id` was unique and an application could have at most one assessment, ever.
- An assessment has a `type`: `interview` or `quiz`. **Both can be created as of Phase 6B-1.** `POST /api/organization/applications/{application}/assessments` with `type=quiz` creates a real `Assessment` + `Quiz` (see section 7a); any other `type` value still fails standard validation.
- An assessment has a `status` (`pending, scheduled, in_progress, completed, declined, cancelled`) and a `result` (`passed, failed, waiting`, or no result yet — represented as `null`, not the string `pending`).
- **`Assessment.result` is a technical outcome, never a recruitment decision (Phase 10A.2).** A Quiz `result = passed` must never, by itself, advance `Application.status`, schedule an Interview, or send an Offer — the organization always takes a separate, explicit action afterward (send an Offer via section 7b; **as of Phase 10A.3**, a real Interview-scheduling action — "Advance to Interview", see below). This restates the existing rule directly above (an assessment's own `status`/`result` never changes `application.status`) specifically for Quiz, because it is the rule Phase 10A.2's entire result-release design exists to protect: releasing a Quiz result to the Student is a visibility change, not a decision, and must never be conflated with one. See section 7a's "Quiz Result Release" subsection for the full mechanism, and section 7a's "Post-Quiz Organization Actions" for what the organization can do once a result is in.
- **`Assessment.result_released_at` (Phase 10A.2)** — nullable timestamp, `null` until the Student is allowed to see `result`. Always `null` for a `type=interview` assessment until `InterviewController::complete()` sets it equal to `completed_at` in the same call that sets `result` — an Interview's result has always been immediately visible to the Student, and this phase preserves that exactly rather than accidentally gating it. For `type=quiz`, see section 7a.
- An organization can create an interview assessment two ways — the original per-type endpoint (`POST /api/organization/applications/{application}/interview`) and, as of Phase 4A-2, the generic endpoint (`POST /api/organization/applications/{application}/assessments` with `type=interview`). **Both call the same underlying workflow** (`App\Services\AssessmentService::createInterviewAssessment()`) and are subject to identical rules: allowed source application status, the active-Assessment invariant (Phase 10A.3 — previously one-assessment-per-application), and the same Interview field validation — see docs/API.md sections 6–7 and docs/ARCHITECTURE.md. A quiz assessment has only the generic endpoint (`type=quiz`), calling the sibling `AssessmentService::createQuizAssessment()`, which reuses the exact same source-status/duplicate/transaction logic.
- Only `shortlisted`, (legacy) `interview_scheduled`, and, **as of Phase 10A.3**, `in_assessment` (with no currently-active Assessment) applications may have an assessment created for them (interview or quiz); `pending`, `reviewed`, `offer_sent`, `accepted`, `rejected`, and `withdrawn` are blocked with a `422`, as is an `in_assessment` application that *does* still have an active Assessment (409, not 422 — see below). `offer_sent` is blocked here specifically because, by construction, it only exists once a real Offer already does — see section 5. Before Phase 10A.3, `in_assessment` itself was excluded from the allowed list, since it could then only ever mean "an Assessment already exists" — see the history subsection below for why that's no longer the only thing it can mean.
- An assessment's own `status`/`result` never changes `application.status`; only the organization's explicit status-update action does that.
- Read endpoints remain: `GET /api/organization/applications/{application}/assessment`, `GET /api/organization/assessments/{assessment}`, `GET /api/student/assessments`, `GET /api/student/assessments/{assessment}` — see docs/API.md section 7. **As of Phase 10A.3**, the first of these returns the full Assessment history (an array), not a single object — see below.

### Assessment History & the Active-Assessment Invariant (Phase 10A.3)

The critical gap this phase closes: before it, "Advance to Interview" (Quiz completed → Organization schedules a follow-up Interview for the same application) was impossible without either destroying the completed Quiz/QuizAttempt or a schema change — because `assessments.application_id` was unique, an application could have at most one Assessment, ever.

- **`assessments.application_id` is no longer unique.** An application can now accumulate real Assessment history: a completed Quiz followed by a genuine new Interview Assessment, both preserved, permanently, as separate rows — see that migration's own doc comment for the full rationale and the trade-off it documents (a partial/conditional unique index was rejected as not portably expressible across this project's MySQL/SQLite connections).
- **At most one *active* Assessment per application, at all times.** "Active" means `status` in `pending`/`scheduled`/`in_progress`; `completed` (and the schema-allowed but not-yet-used `declined`/`cancelled`) is final and never blocks a new Assessment. This is now an application-level invariant enforced by `AssessmentService` — row-locking the parent `Application` (`lockForUpdate()`, the same discipline `OfferService::respondToOffer()` already uses) inside the creation transaction, then checking the full history for an active row — not a database constraint, since one can no longer exist once history is allowed.
- **"Advance to Interview" is not a new capability with a new endpoint.** It is exactly the existing `POST /api/organization/applications/{application}/interview` (or the generic endpoint with `type=interview`) — the same `AssessmentService::createInterviewAssessment()` every Interview creation already uses, now legal for an `in_assessment` application whose most recent Assessment (typically a completed Quiz) has been finalized. The Flutter client reuses its existing real Schedule Interview screen for this, rather than building a new one.
- **`Application.status` stays `in_assessment` throughout.** Advancing a completed Quiz to a new Interview leaves the application at the same `in_assessment` value it was already at — `AssessmentService::transitionToInAssessment()` is a safe no-op write in that case, never a second/different status. No new Application status was introduced for "quiz then interview" — see section 8.
- **Nothing is ever deleted or overwritten** to make room for a follow-up Assessment. The completed Quiz, its Questions, and its QuizAttempt all remain exactly as they were, queryable via `GET /api/organization/applications/{application}/assessment`'s full history array alongside the new Interview.
- **Rejecting an application never touches Assessment history** — the existing generic status-update action; Assessment rows (and their Interview/Quiz/QuizAttempt children) are untouched regardless of `Application.status`.
- **Deleting an Interview Assessment (`DELETE /api/organization/interviews/{interview}`) no longer blindly reverts `Application.status` to `shortlisted`.** Before Phase 10A.3 this was always safe, since the deleted Assessment was necessarily the application's only one. Now, it only reverts to `shortlisted` if the application has *no* Assessment left at all after the deletion — if an earlier completed Quiz still exists, the application correctly stays `in_assessment`, since the organization can still act on that completed Quiz (Send Offer, Reject, or advance to a new Interview again).
- **Offer eligibility follows the current (latest) Assessment only** — see section 7b for the full rule and worked examples. This is the rule that makes "advance to Interview, but don't let an old completed Quiz still authorize an Offer" correct.

## 7a. Quiz Rules (Phase 6B-1 organization authoring; Phase 6B-3 student taking/grading)

Quiz v1 covers both organization authoring (creating a quiz assessment, adding/editing/removing its questions, and publishing it — Phase 6B-1) and student taking (starting the one attempt allowed, submitting it, and immediate server-side auto-grading — Phase 6B-3).

- A quiz belongs to one assessment; an assessment can have **at most one quiz**, enforced by a database unique constraint (`quizzes.assessment_id`) — reached via `Application → Assessment → Quiz` (there is no direct `Application`-to-`Quiz` relationship). **As of Phase 10A.3**, an application itself can accumulate more than one quiz over its lifetime *if* the organization creates a second Quiz-type Assessment after finalizing the first (the generic backend capability permits this, the same as any other follow-up Assessment — see section 7's "Assessment History & the Active-Assessment Invariant" — though the Flutter "Advance to Interview" action specifically only ever creates a follow-up Interview, never a second Quiz). **As of Phase 10A.4B**, this "one Quiz, one Assessment" shape is the *legacy* one of two — see "Shared Quiz Template" below for the other, where one Quiz is instead referenced by many candidates' Assessments.
- A quiz has a lifecycle independent of `Assessment.status`: `draft` → `published`. It always starts `draft`. Creating a quiz assessment sets `Assessment.status = pending`; publishing the quiz (and only publishing it) advances `Assessment.status` to `scheduled` — publishing never touches `Application.status`, which is already `in_assessment` from creation and stays there.
- `Quiz.passing_score` is a **required integer percentage, 0–100**, set at creation and immutable afterward in v1 (no update-quiz-configuration endpoint exists).
- **Question display order is not the same as `Question.position` (Phase 10A.2).** The Organization authoring UI never sends an explicit `position` (it defaults to `0` server-side for every question), so real quizzes typically have every question sharing the same `position`. The backend's contract is only ever a stable *order* — `orderBy('position')->orderBy('id')` — never a reliable *display number*; a 1-based question number must be derived by the consuming client from that returned order, never from the raw `position` value. This is a rendering concern the backend does not solve by renumbering `position` itself, since `position` is also the organization's own (currently unused) reordering hook for a future authoring UI.
- **Quiz display mode (Phase 10A.2)**: `display_mode` (`single`/`paginated`/`all`, default `all`) and `questions_per_page` (required only when `display_mode = paginated`) are organization-authored, stored on `Quiz`, and returned to both roles. The backend does not itself paginate any response — `GET .../quiz` and the Student equivalent always return the full `questions` array regardless of `display_mode`; pagination is a client-side rendering concern driven by these two fields, the same posture as the question-numbering rule above. Both default to the pre-10A.2 behavior (`all`) so an existing quiz's rendering is unaffected until an organization deliberately changes it.
- A quiz has zero or more questions (`hasMany`). Quiz v1 supports exactly two question types: `multiple_choice` and `true_false`. Both are **auto-graded only** — there is no short-answer type and no manual-grading path.
- `multiple_choice` questions store their choices in `options` (a JSON array, minimum two entries) and a `correct_answer` that must exactly match one submitted option (case-sensitive — options are free-form organization-authored text). `true_false` questions never store `options` (always `null` in the database — see docs/ARCHITECTURE.md for why this representation was chosen over serializing `["True", "False"]`); their two choices are fixed and implicit. A `true_false` `correct_answer` is canonicalized to exactly `"True"`/`"False"` regardless of the input casing submitted (`"true"`, `"TRUE"`, `"1"`, etc. all normalize the same way).
- **`Question.correct_answer` is organization-internal.** It is safe to return to the organization that authored the quiz (every organization-facing Quiz/Question response includes it), but it **must never be included in any Student-facing Quiz API response** — see `Question::ORGANIZATION_ONLY_FIELDS`, `App\Http\Controllers\Student\Concerns\HidesInternalQuestionFields`, and `tests/Unit/Models/QuestionPrivacyTest.php`. As of Phase 6B-3 this is enforced on every student-facing path that can nest a quiz: `GET /student/assessments/{assessment}/quiz`, `GET /student/assessments`, and `GET /student/assessments/{assessment}` — never just the dedicated Quiz endpoint.
- Questions may only be added, updated, or deleted while `quiz.status = draft`. Once `published`, all three are rejected with `422` (`"Published quizzes cannot be modified"`), and quiz configuration itself (title/instructions/time limit/passing score) is likewise treated as immutable in v1 — there is no update-quiz endpoint at all, published or not.
- Publishing (`PUT /api/organization/quizzes/{quiz}/publish`) requires: the quiz belongs to the requesting organization, `quiz.status = draft`, and at least one question exists. Every question is already structurally valid by construction (both create and update are gated by the same validation), so publish performs no further per-question re-validation.
- There is currently no dedicated Quiz/Assessment delete endpoint (the only existing Assessment cleanup path is `InterviewController::destroy()`, which is interview-specific). Deleting an `Assessment` still correctly cascades to its `Quiz`, `Question`, and (as of Phase 6B-3) `QuizAttempt` rows at the database level (`cascadeOnDelete` on every foreign key) — this is proven directly against the models in tests — but no organization-facing route exercises it for quiz today, which means **a quiz stuck in `draft` has no way to be cancelled/removed in this phase.** This is a known, deliberately deferred gap (see docs/ARCHITECTURE.md), not an oversight.

### Student Quiz Taking (Phase 6B-3)

The student workflow: **published quiz → start → attempt in progress → submit → auto-grade → Assessment `completed` → `passed`/`failed`.** There is no student-facing draft-quiz visibility, no retake, no manual grading, and no answer-review endpoint (a submitted attempt's correct answers are never returned to the student).

- **One attempt only.** `quiz_attempts.(quiz_id, application_id)` is a database unique constraint, not just an application-level check — a genuine concurrent double "Start" race is resolved by catching the resulting integrity violation and returning the winning attempt, the same translated-`QueryException` pattern `AssessmentService` already uses for duplicate assessments.
- **No separate attempt-status column.** An attempt's state is derived, not stored: no row at all means "not started"; `submitted_at === null` means "in progress"; `submitted_at !== null` means "completed" (and graded). See docs/ARCHITECTURE.md for the full reasoning.
- **Start is idempotent for an in-progress attempt.** Calling Start again while unsubmitted returns the *same* attempt — `started_at` is never reset and no extra time is ever granted. This is what lets the client safely re-open/refresh mid-attempt without it costing the student anything. A submitted attempt can never be restarted (no retakes in v1) — Start on an already-submitted quiz returns `409` (`"Quiz has already been submitted"`).
- **Start never changes `Application.status`.** It moves `Assessment.status` to `in_progress` only; the application was already `in_assessment` (set at quiz-assessment creation, Phase 6B-1) and stays there through the entire attempt.
- **Server-enforced time limit, never client-trusted.** When `quiz.time_limit_minutes` is set, a submission is only accepted while `now() <= attempt.started_at + time_limit_minutes`, checked entirely server-side with no grace period. An expired submission is rejected with `422` (`"Quiz time limit has expired"`) and the attempt is left unsubmitted (a student cannot be locked out of ever getting a graded result by an expired timer — retrying isn't possible in v1, but the rejection itself never corrupts attempt state). A `null` time limit never expires. The Flutter countdown (a later phase) is a UI convenience only.
- **Grading is entirely server-side, from each question's own `correct_answer`.** The submission body only ever supplies `question_id`/`answer` pairs (see `App\Http\Requests\Student\SubmitQuizRequest`) — `points`, `score`, and `correct_answer` are never accepted as client input and are never read from the request even if sent.
- **Every quiz question must be answered exactly once** to submit at all — no partial submission in v1. `SubmitQuizRequest` rejects a missing question, a duplicate `question_id`, a `question_id` that doesn't belong to the quiz, an MCQ answer that isn't one of the question's own `options`, and a `true_false` answer that isn't `"True"`/`"False"` (canonicalized the same way `correct_answer` is on the organization side — `"true"`/`"TRUE"`/`"1"` and the false equivalents all normalize identically before validation).
- **Scoring**: `score = round(earned_points / total_points * 100)`, an integer percentage. `earned_points` sums `question.points` for every question whose submitted answer exactly equals `question.correct_answer`; `total_points` sums every question's `points`. Rounding uses PHP's `round()` default (round-half-away-from-zero) — e.g. exactly 12.5% rounds to 13, not 12.
- **Result**: `score >= quiz.passing_score` → `Assessment.result = passed`; otherwise `failed`. Both happen atomically with `Assessment.status = completed` and `Assessment.completed_at = now()` inside the same database transaction that saves the attempt's `answers`/`score`/`submitted_at` — a genuine concurrent double-submit is caught by row-locking the attempt (`lockForUpdate()`) before checking `submitted_at`, returning `409` (`"Quiz has already been submitted"`) the same as a simple repeat request. **The result is always computed at this moment, regardless of `result_release_mode`** — release mode only ever governs when the Student is shown it (see "Quiz Result Release" below); it never delays or affects grading itself.
- **Submit without Start is rejected**, not implicitly treated as a fresh start — `422` (`"Start the quiz before submitting."`). Phase 6B-3 deliberately keeps Start and Submit as two distinct, required steps.
- **`Application.status` is never touched by grading.** It remains `in_assessment` after a quiz is submitted and graded, exactly like it does after an interview is completed (section 6) — the final accepted/rejected decision always stays a separate, organization-triggered action via the existing status endpoint, never automatic from a quiz result.

### Quiz Result Release (Phase 10A.2, made decision-aware in Phase 10A.4A)

Governs *when* a graded Quiz result becomes visible to the Student. As of Phase 10A.4A this is no longer just a timing question — a manual E2E finding showed that "technically correct release timing" was not enough: a Student could receive a bare pass/fail with no indication of what happens next. The rule is now: **a Student-facing update releases only once the technical result *and* a real Organization next-step decision are both ready.**

- **Four concepts, never merged**: (A) the Quiz score, (B) the technical result (`passed`/`failed`), (C) the Organization's next-step decision (`interview`/`offer`/`reject` — `Assessment.next_action`), (D) the Student-facing release of the combined outcome. A released result is still never itself a recruitment decision (see section 7's restated rule) — (D) just means the Organization's own (C) has become visible, not that (C) was computed automatically from (B).
- `Quiz.result_release_mode` is `manual`, `immediate` (default), or `scheduled`, set at quiz-assessment creation alongside `passing_score` and otherwise immutable in v1, same as the rest of quiz configuration. As of this phase, all three modes describe *when*, given both grading and the decision are ready — none of them can release on grading readiness alone anymore.
- `immediate`: released the instant **both** are ready, whichever happens second. If the Student submits before a decision exists (the common case), the result stays pending; the moment the Organization's decision later becomes ready, that same request releases it immediately — no extra "release" step, and no waiting for a job or another day.
- `manual`: never released automatically regardless of readiness. The organization releases it explicitly via `PUT /api/organization/assessments/{assessment}/release-result` whenever it chooses to (docs/API.md section 7) — which itself now requires a ready decision (422 otherwise).
- `scheduled`: requires `result_release_at` (a future datetime at creation time), and now additionally requires a ready decision. Release is driven by a real delayed queue job (`App\Jobs\ReleaseQuizResultJob`), dispatched with `->delay($quiz->result_release_at)` when the quiz is **published** — backed by this project's existing `QUEUE_CONNECTION=database` + `jobs` table, not a cron/`Schedule::` job. **The forgotten-decision case**: if the scheduled time arrives with no decision yet, the job does not release anything — the Student stays exactly "Assessment Submitted / Result Pending", with no leak of score/pass-fail/interview/offer/reject and no email/notification sent to them. Instead, the job sends the Organization a one-time "Decision Required" reminder (deduplicated via `decision_reminder_sent_at`, so a retried job never sends it twice). Once the Organization later completes the decision — even hours or days after the scheduled time — that decision-completing request itself detects the scheduled time has already passed and releases immediately, exactly like the `immediate`-mode case above: no re-editing the release time, no waiting for another scheduled run.
- **A manual release is always allowed regardless of `result_release_mode`**, but now still requires a ready decision — `PUT .../release-result` checks "is it completed" (422 if not), "is a decision ready" (**422 as of Phase 10A.4A** — `"A next-step decision (Advance to Interview, Proceed to Offer, or Reject) must be selected and ready before releasing this result."`), and "is it already released" (409 if so).
- **Decision readiness (`QuizResultReleaseService::isNextActionReady()`)**: `interview` is ready only once the real follow-up Interview Assessment it staged has all the same required scheduling fields any other Interview requires (reused validation, never placeholder data). `offer` is ready once its staged terms passed the same validation the real Offer flow requires. `reject` is ready as soon as the Organization explicitly confirms it — no additional data needed.
- **The one place `result_released_at` is ever set, for any mode or path, is the private `release()` method inside `App\Services\QuizResultReleaseService`**, reached only through `attemptRelease()` (submit, a decision-completion call, and the scheduled job) or `releaseManually()` (the explicit organization endpoint) — both funnel through the same readiness check and the same `release()`. It re-locks the Assessment row and re-checks readiness inside its own transaction, so a delayed job racing an Organization action, a double-click on Release, or a retried queue job can only ever actually release once — the loser silently no-ops. This is the same "one authoritative check, every path shares it" pattern `AssessmentService`/`OfferService` already establish elsewhere in this document.
- **Exactly one Student-facing communication per release, matching whichever decision was made** — never a generic "you passed" plus a separate "interview scheduled"/Offer/rejection message. `release()` dispatches by `next_action`: `interview` sends one new combined notification/email ("Assessment Update — Interview Invitation", congratulating the Student and including the real interview details in the same message); `offer` calls the exact same `OfferService::sendOffer()` a direct Offer already uses, so its own existing Offer notification/email fires once, with no separate quiz-result message layered on top; `reject` applies the same status transition and reuses the existing respectful rejection notification/email, once — never an aggressive "FAILED" framing. The pre-10A.4A `notifyQuizResultAvailable`/`QuizResultMail` pair (a standalone "here's your quiz result" message) is superseded and no longer reachable from any of these three paths, though it remains defined (its own tests still pass) rather than deleted.
- **The Organization's own view of `result`/`score` is never gated by any of this.** `result_release_mode`/`result_released_at`/`next_action` only ever affect what a Student-facing endpoint returns; every Organization-facing Assessment/Quiz endpoint (docs/API.md section 7/7a) always returns the real, current `result`, the real attempt `score`, and the real staged decision, regardless of mode or release state.
- **Backward compatibility**: a Quiz Assessment released before this phase (`result_released_at` already set, `next_action` still `null`) is a completed legacy release and stays fully readable exactly as before — nothing retroactively hides it, and it is never required to backfill a `next_action` it never had.
- **Pass/Fail never forces a next action.** A passed result may still lead to Interview, Offer, or Reject; a failed result may normally lead to Reject but the Organization retains the same override authority it already had before this phase (section 7b: `Assessment.result` was never a precondition for sending an Offer, and stays that way) — the UI may warn, but the backend never hard-blocks an Organization's chosen next action based on `result` alone.

### Post-Quiz Organization Actions (Phase 10A.2; Advance to Interview implemented Phase 10A.3; staged as a decision in Phase 10A.4A)

Once a Quiz assessment is `completed`, the organization chooses its next-step decision — the same three real actions as before this phase, now staged before release rather than executed immediately, via `POST /api/organization/assessments/{assessment}/next-action/{interview,offer,reject}` (docs/API.md section 7):

- **Advance to Interview** — stages the real transition first introduced in Phase 10A.3 (an application may have more than one `Assessment` over its lifetime; `assessments.application_id` is non-unique — see that migration's own doc comment). The real follow-up Interview `Assessment` is created immediately, via the exact same `AssessmentService::createInterviewAssessment()` every other Interview creation uses (same validation, same active-assessment invariant), with `origin_assessment_id` pointing back at the Quiz — but the Student is not notified and cannot see it through any Student-facing endpoint until release (`Assessment::isPendingDecisionRelease()`). Nothing is destructively deleted; the completed Quiz/QuizAttempt is untouched. The Flutter client reuses its existing real Schedule Interview screen for this action rather than a new one.
- **Proceed to Offer** — stages the decision with the same validated terms the real Offer flow requires, but creates **no real `Offer` row yet** — nothing is sent to the Student, and there is nothing to accidentally leak early. The real `Offer` is created for the first time at release, by calling `OfferService::sendOffer()` unchanged — no parallel "staged Offer" implementation to keep in sync with the real one.
- **Reject** — stages the decision as a bare confirmation; `application.status` is not changed and the Student is not notified until release, at which point the existing generic rejection transition and its respectful notification/email apply exactly as they always have. Rejecting never deletes or alters Assessment history (see section 7's Assessment History rules).
- **A decision may be corrected before release** — the same endpoint may be called again with a different action (e.g. Interview staged, then switched to Reject) or the same action with corrected details (e.g. a wrong Interview date). If the *previous* decision was Interview, its now-abandoned staged Interview Assessment is discarded first — otherwise it would remain a genuine `status=scheduled` (active) Assessment forever, permanently blocking the active-assessment invariant for this application even though it was never released or seen by the Student. Once released, a decision is final — none of the three endpoints are reachable anymore (409).
- **None of the three change `application.status` at staging time** — only at release, and only Offer/Reject actually change it (an Interview decision's `application.status` was already set to `in_assessment` when the follow-up Assessment was created, matching the existing direct-Interview flow exactly).

### Shared Quiz Template (Phase 10A.4B)

**The problem this closes**: before this phase, a Quiz was always authored per-candidate. If an Opportunity used `recruitment_process = quiz` and received 50 applicants, the Organization would have had to author the same title/instructions/questions 50 separate times. Now a Quiz definition is authored ONCE per Opportunity and referenced by every candidate's own Assessment.

- **A Quiz row is always exactly one of two mutually exclusive shapes** — legacy (`assessment_id` set, `opportunity_id` null, the shape section 7a already describes) or shared template (`opportunity_id` set, `assessment_id` null; `quizzes.opportunity_id` is unique — at most one template per Opportunity). Never both, never neither. The pre-10A.4B ad-hoc "Choose Assessment" flow is completely unchanged by this phase — it still always creates a legacy-shaped Quiz, even for an Opportunity whose `recruitment_process` happens to be `none`.
- **Questions are never duplicated per candidate.** A shared template's Questions are authored once, through the exact same question CRUD endpoints (and the exact same `draft`-only immutability rule) the legacy flow already uses — see docs/API.md's "Shared Quiz Template" section for how ownership resolution branches to make this work unchanged.
- **`QuizAttempt` needed no schema change at all.** It was already unique on `(quiz_id, application_id)`, not `(assessment_id, application_id)` — exactly the shape multiple candidates sharing one Quiz row requires. Score/answers were already, and remain, fully isolated per candidate.
- **Candidate advancement is a separate action from Quiz creation.** `POST /organization/applications/{application}/quiz-assessment` creates only a new Assessment referencing the already-published shared Quiz — never a new Quiz row, never duplicated Questions. Fails with a clear `422` (`"This opportunity's quiz is not published yet."`) if the Opportunity has no template yet, or one that's still `draft` — an Opportunity that requires Quiz must never silently send a candidate into a missing/unfinished Quiz.
- **The Student "Quiz Available" notification/email fires per-candidate, at advancement time — never at template-publish time, and never for every applicant just because the Opportunity has a Quiz.** Publishing the template itself notifies nobody (no candidate has an Assessment yet); the exact same `notifyQuizPublished()` call the legacy flow already uses just fires later and individually, once per advanced candidate.
- **The scheduled-release job is dispatched per candidate, not once per Quiz.** Before this phase, one Quiz always had exactly one Assessment, so dispatching the release job once at publish time was equivalent to dispatching it once per Assessment. That equivalence breaks for a shared template — dispatch now happens at *advancement* time (when each candidate's own Assessment first exists), keyed by that Assessment's id, not the Quiz's id (`App\Jobs\ReleaseQuizResultJob`).
- **`result_release_mode`/`result_release_at` are the one general announcement policy every candidate reads identically off the shared Quiz row** — e.g. "no earlier than Aug 30, 6pm for everyone" — while each candidate's own decision-readiness (section above) still gates independently. If the shared time passes and candidate A has a ready decision while candidate B doesn't, A releases and B stays pending — the exact same per-Assessment readiness rule as the legacy flow, unmodified; nothing about `QuizResultReleaseService` itself changed for this phase.
- **A decision may still be corrected before release, and Offer/Interview/Reject remain candidate-specific**, even though the underlying Quiz is shared — two candidates on the same shared Quiz can have completely different outcomes (one advances to Interview, one gets a direct Offer, one is rejected) with zero cross-candidate interference. A shared Quiz never implies a shared hiring decision.
- **Interview details are always candidate-specific**, exactly as before — a shared Quiz never carries interview scheduling of any kind; each candidate's own staged/released Interview Assessment carries its own date/time/type/link independently.
- **No mass/batch decision action exists.** The Organization-level Quiz Results view (`GET /organization/opportunities/{opportunity}/quiz/results`, docs/API.md) surfaces every candidate's score/result/decision/release state in one place so decisions are efficient to make, but each decision is still made individually, per candidate, through the existing real decision endpoints — there is no "advance every passed candidate to Interview" action.
- **Published-quiz immutability is the same rule as the legacy flow, unconditionally** — once `published`, a template's settings and questions are frozen, full stop, regardless of whether any candidate has attempted it yet. No "published but still editable because unused" state was introduced — matching the "smallest safe architecture" this phase deliberately keeps to.
- **Historical, pre-10A.4B Quiz data is untouched.** No backfill, no migration of existing legacy Quiz rows into the shared-template shape, no forced reattachment to a new Opportunity Quiz. A completed candidate-specific Quiz from before this phase remains readable exactly as it always was.

### Candidate Availability Window (Phase 10A.4B addendum)

**The problem this closes**: a shared Quiz template is authored once, but every candidate is advanced to it at a different moment. Without a per-candidate schedule, either every candidate would share one fixed availability window (unfair — a candidate advanced a week later gets less notice) or the Organization would have to manually track each candidate's own dates. Instead, one shared *policy* on the Quiz produces a different, real, frozen schedule for each candidate automatically.

- **The policy is shared; the schedule is not.** `availability_delay_days`/`availability_time`/`submission_window_hours` live on the shared Quiz template (configured once, required at creation). `available_at`/`due_at` — the actual computed dates — live on each candidate's own `Assessment`, computed **once**, at "Advance to Quiz" time, and never recalculated afterward. Editing the policy later (only possible while the template is still `draft`, per the existing immutability rule) can never retroactively move an already-advanced candidate's dates, because by the time any candidate has been advanced, the template can no longer be edited anyway.
- **Assignment is the only trigger — merely applying grants nothing.** A Student's window doesn't start counting down until the Organization explicitly calls `POST /organization/applications/{application}/quiz-assessment` (the same "Advance to Quiz" action from the base phase above). Publishing the template itself still notifies nobody, exactly as before.
- **The Student notification/email at assignment now carries the real schedule** — reusing the exact same `notifyQuizPublished()`/`QuizAvailableMail` machinery the base phase already established, extended with truthful `available_at`/`due_at`/time-limit content when a window applies. No second email is ever sent when the window later opens — this would be spam for a fact the Student was already truthfully told about in advance.
- **Two independent constraints gate submission**: the candidate's personal timer (`time_limit_minutes` after their own `started_at`, if the Quiz has one) and their own submission deadline (`due_at`, if the policy produced one). The *effective* cutoff is whichever comes first — a generous personal timer never overrides an earlier hard deadline, and a late `due_at` never grants extra time beyond an already-tighter personal timer. See docs/API.md's "Candidate Availability Window" section for the exact worked example.
- **A missed deadline is purely a timing fact, never an invented outcome.** No automatic `assessment.result`, no automatic Application rejection, no fabricated "failed" — the Organization retains full recruitment authority over what happens to a candidate who never submitted, exactly as it already does for every other non-outcome in this flow. The Student sees a truthful "Assessment Deadline Passed" state; nothing more is claimed.
- **Result release remains entirely independent of availability/deadline**, exactly as section 7's release rules already establish for the base shared-quiz-template case — a candidate's `available_at`/`due_at` govern only whether they *can submit*, never when their (separately-gated) result becomes visible.
- **Security**: the backend is the sole authority. A Student cannot start early or submit past the effective cutoff via a direct API call regardless of what the Flutter client shows — `Start`/`Submit` independently re-check `available_at`/`due_at`/the personal timer server-side every time. Question text is never returned before `available_at` on any endpoint that nests `quiz.questions` — a disabled Flutter button is UX, not the real gate.
- **Backward compatibility, exactly matching the base phase's own convention.** Every Assessment that predates this addendum (and every legacy ad-hoc Quiz Assessment created after it) simply has `available_at`/`due_at` both `null` — read as "no gating", not as missing/invalid data. No backfill, no retroactive invalidation.

## 7b. Offer Rules (Phase 6C-1)

The final hiring decision. An Offer is the organization's own final action on
an `in_assessment` application with a completed Assessment; the student's
accept/decline response is the application's own final action in turn. Owned
end-to-end by `App\Services\OfferService`, the same "one service owns every
multi-model transition" doctrine `AssessmentService` already established.

- **One Offer per Application**, enforced by a database unique constraint
  (`offers.application_id`) — unlike `Assessment` (Phase 10A.3), an
  application never accumulates Offer history; there is exactly one Offer,
  ever, per application.
- **An Offer has a `status`: `sent`, `accepted`, or `declined`.** No `draft`
  (an Offer is created and sent in one organization action — no multi-step
  authoring to protect against, unlike Quiz), no `expired` (v1 has no
  automatic expiry, and therefore no `expires_at` field either — an Offer
  stays `sent` indefinitely until the student responds), and no `cancelled`
  (v1 gives the organization no way to rescind a sent Offer). Every Offer's
  entire lifecycle is: created `sent`, then terminates exactly once via
  accept or decline. None of this is enforced by a background job or
  scheduled task — there is nothing time-based to enforce.
- **Send-offer eligibility**: `application.status` must be exactly
  `in_assessment`, and its **current (latest) Assessment** must exist and
  have `status = completed`. `pending`/`reviewed`/`shortlisted` (no
  assessment reached yet), `offer_sent`/`accepted`/`rejected`/`withdrawn`
  (past this stage already), and legacy `interview_scheduled` (never itself
  `in_assessment`, even with a completed Assessment attached — see section
  5) are all rejected with `422`. An `in_assessment` application whose
  current Assessment is still `pending`/`scheduled`/`in_progress` (or,
  defensively, missing entirely) is likewise rejected with `422`.
  - **"Current (latest) Assessment" — the Phase 10A.3 rule that matters
    once an application can have Assessment history.** `OfferService`
    reads `Application::assessment`, which resolves to the most recently
    created Assessment (`hasOne(...)->latestOfMany()` — see that model's
    own doc comment), never an arbitrary or the *first* one. This is what
    correctly implements every case: a completed Quiz with no follow-up →
    it's the latest → eligible. A completed Quiz advanced to a new
    Interview that's still `scheduled`/`in_progress` → the Interview is now
    the latest, and isn't `completed` → blocked (**this is the regression
    this rule specifically exists to prevent**: an old completed Quiz must
    never satisfy Offer eligibility once a newer Assessment exists and
    hasn't finished). That Interview completed → it's the latest and is
    `completed` → eligible again. `Assessment.result` is still never
    inspected anywhere in this chain — see the rule below.
- **`Assessment.result` is informational only and never gates sending an
  Offer.** `passed`, `failed`, `waiting`, and no result at all (`null`) are
  all equally eligible — the organization retains final hiring authority;
  a completed Assessment (regardless of outcome) is the only precondition.
  This is a deliberate business decision, not an oversight: a candidate who
  fails a quiz might still be the right hire on other merits, and the
  reverse (a passing result) never *obligates* an offer either.
- **Sending an Offer sets `Application.status = offer_sent`** in the same
  transaction that creates the Offer (`status = sent`, `sent_at = now()`) —
  written from exactly one place, `OfferService::sendOffer()`. Neither
  `Assessment.status` nor `Assessment.result` is touched by this or any
  later Offer transition.
- **The student accepts or declines exactly once.** Accepting sets
  `Offer.status = accepted`, `responded_at = now()`, and
  `Application.status = accepted`. Declining sets `Offer.status = declined`,
  `responded_at = now()`, and `Application.status = rejected` — the same
  final status a direct organization rejection produces (section 5); only
  the actor and `Offer.status` distinguish which happened. Both transitions
  lock the Offer row (`lockForUpdate()`) for the duration of the response
  transaction, so a genuine concurrent double-response (two accepts, two
  declines, or an accept racing a decline) always has exactly one winner —
  the second read finds `status` no longer `sent` and fails with `409`,
  never producing a state where `Offer.status` and `Application.status`
  disagree (e.g. Offer `accepted` alongside Application `rejected`).
- **No re-response.** Neither accept nor decline may be called again once
  the Offer has already been responded to, regardless of which response
  "won" — `409`.
- **Compensation fields are optional but internally consistent.** An Offer
  with no compensation terms at all is valid v1 data (e.g. an unpaid/
  volunteer role). If `salary_amount` is provided, `salary_currency` and
  `salary_period` (`hourly`/`monthly`/`yearly`) are both required; either of
  those being supplied without `salary_amount` is rejected the same way —
  never a silently-incomplete compensation shape.
- **`start_date`, if provided, must be today or a future date** — a start
  date already in the past would never make sense for an Offer that hasn't
  been accepted yet.
- **All v1 Offer fields are student-visible** on the student's own Offer —
  there is no organization-internal-only field (no `internal_notes`), so no
  field-hiding is needed the way `Question.correct_answer`/`Interview`'s
  organization-only fields are hidden from students elsewhere in this app.
  A student may only ever see their own Offer; an organization may only ever
  see Offers for its own opportunities — both enforced the same uniform
  "404, never revealing which case applies" way every other ownership check
  in this app already is.
- **No update/delete/cancel/resend action exists for an Offer in v1** — once
  sent, its terms are immutable, and its only two possible futures are
  accepted or declined.
- **(Phase 6C-4) Once an Offer exists, the organization's generic
  `PUT /api/organization/applications/{application}/status` endpoint can no
  longer move the Application at all** — including to `rejected`, which is
  otherwise a valid request to that endpoint (section 5). This is the
  direct consequence of v1 having no Offer cancel/rescind action: allowing
  a generic reject to succeed after an Offer was sent would let
  `Offer.status = sent` and `Application.status = rejected` coexist, an
  impossible combination the row-locked accept/decline transaction above
  already goes to considerable lengths to prevent from the student side.
  The organization's only remaining lever once an Offer exists is to wait
  for the student's response — see section 5's Offer/Application integrity
  rule.

## 8. Notification Rules

- Notifications belong to users.
- Notifications are created when important events happen.
- Examples:
  - organization approved
  - application submitted
  - application reviewed
  - interview scheduled
  - application accepted or rejected
- Users can mark notifications as read.
- Notifications can have a priority level (low, normal, high) and record the timestamp they were sent.
- **A user may permanently delete their own notifications (Phase 9.1) — one at a time, or in bulk for every currently-read one.** This is inbox cleanup only: `notifications` has no foreign key pointing at it from any other table, so deleting a notification can never affect the Application/Invitation/Assessment/Interview/Offer/EducationVerification row it was originally about, and never reverses the business event itself. Bulk deletion is deliberately scoped to *read* notifications only (`DELETE /api/notifications/read`) — an unread notification is never silently removed, so a user can never lose an update they haven't seen yet.
- **`notifications.type` supports 7 values as of Phase 7A-1**: `system`, `application`, `interview`, `assessment`, `offer`, `organization`, `opportunity`. `assessment` (Quiz-availability/completion) and `offer` (the Offer lifecycle) were added this phase — see the migration `2026_08_11_090000_add_assessment_and_offer_types_to_notifications_table` — because neither concern was precisely representable by the original 5 values without overloading `interview`/`application` for something they don't actually describe.
- **`App\Services\NotificationService` (Phase 7A-1) is the one backend API for creating a Notification row.** It exposes a generic `create()` plus one narrowly-scoped convenience method per recommended event (`notifyApplicationSubmitted`, `notifyApplicationShortlisted`, `notifyApplicationRejected`, `notifyInterviewScheduled`, `notifyInterviewRescheduled`, `notifyQuizPublished`, `notifyQuizResultAvailable`, `notifyQuizCompleted`, `notifyOfferSent`, `notifyOfferAccepted`, `notifyOfferDeclined`, and, **as of Phase 10A.4A**, `notifyQuizDecisionInterview`/`notifyDecisionRequired` — see below) — each resolving fixed, concise copy, the correct `type`/`priority`, and an app-relative Flutter route path (`action_url`) before calling `create()`. `create()` validates `type`/`priority` against the real enum values and throws `InvalidArgumentException` before ever reaching the database on a bad value. No Laravel Events/Listeners/Observers/Jobs are used — every call is a plain synchronous method call, matching this project's "one service owns this concern" doctrine (`AssessmentService`, `OfferService`) at its current scale. `notifyQuizResultAvailable` (student-facing) was added in Phase 7A-2 alongside the wiring below, distinct from the pre-existing `notifyQuizCompleted` (organization-facing) — the same underlying event, two different recipients/copy. **As of Phase 10A.4A, `notifyQuizResultAvailable` is superseded** by the decision-aware release communications below (see "Quiz Result Release" above) — it remains defined and its own unit tests still pass, but is no longer reached from the standard release path. As of Phase 7A-4.1 (extended Phase 7A-4.2), `NotificationService` also constructor-injects `EmailService` and, from inside seven of its eleven original convenience methods, queues a transactional email alongside the in-app row — see the dedicated rule below.
- **Two new events as of Phase 10A.4A, both reusing the existing `assessment` notification type (no migration needed):** `notifyQuizDecisionInterview()` (student-facing, `priority=high`) fires exactly once, from inside `QuizResultReleaseService::release()`'s Interview branch, as the one combined "Assessment Update" communication — never a separate "you passed" plus a separate "interview scheduled" pair (its paired Mailable is `App\Mail\AssessmentDecisionInterviewMail`, subject "Assessment Update — Interview Invitation"). `notifyDecisionRequired()` (organization-facing, `priority=high`, in-app only — deliberately no email, matching the low-urgency/internal-review nature of the other organization-facing in-app-only events below) fires from `QuizResultReleaseService::sendDecisionReminder()`, only when a `scheduled` release's time has passed with no decision yet, deduplicated per-assessment via `decision_reminder_sent_at` so a retried scheduled job never sends it twice; its `action_url` points at the real Organization Application Details route.
- **Wired into the real workflow as of Phase 7A-2.** Every notification below is transition-based (fires only on a genuine first-time state change), not request-based (a request that re-asserts an already-current state creates nothing) — there is no separate deduplication table; correctness comes entirely from each integration point's own transition/guard logic, proven by `tests/Feature/Notifications/WorkflowNotificationTest.php`.
  - **Student-facing**: `Organization\ApplicationController::updateStatus()` — shortlisted (`notifyApplicationShortlisted`) and rejected (`notifyApplicationRejected`), each only when the request status differs from the application's current status (a `reviewed` transition, or a re-request of the already-current status, notifies nobody); blocked entirely once an Offer exists (section 5), so this can never double-fire alongside an Offer decline. `AssessmentService::createInterviewAssessment()` — interview scheduled (`notifyInterviewScheduled`), emitted once from this shared service method itself (both the legacy `POST .../applications/{application}/interview` route and the generic `POST .../applications/{application}/assessments` `type=interview` route delegate here, so notifying from either controller instead would risk a double notification). `Organization\InterviewController::update()` — interview rescheduled (`notifyInterviewRescheduled`), only when `scheduled_at` or `interview_type` actually changes (a logistics-only edit — `meeting_link`/`location`/`interviewer_name`/`notes` — does not count as a reschedule). `Organization\QuizController::publish()` — quiz available (`notifyQuizPublished`), pointing directly at the Student Quiz route (`/student/assessments/{assessmentId}/quiz`), the one `action_url` in this phase that isn't an Application Details path. **As of Phase 10A.2**, quiz result available (`notifyQuizResultAvailable`) no longer fires unconditionally from `Student\QuizController::submit()` on every first grading — it fires only from inside `App\Services\QuizResultReleaseService::release()`, whichever of the three release paths (submit-time immediate release, the scheduled `ReleaseQuizResultJob`, or an organization's manual release via `PUT .../release-result`) actually triggers it, and never fires a second time for the same assessment (see section 7a's "Quiz Result Release"). `OfferService::sendOffer()` — offer sent (`notifyOfferSent`).
  - **Organization-facing**: `Student\ApplicationController::store()` — new application (`notifyApplicationSubmitted`), inside the same transaction as the Application insert. `Student\QuizController::submit()` — quiz completed (`notifyQuizCompleted`), alongside the student's own `notifyQuizResultAvailable` in the same transaction. `OfferService::acceptOffer()`/`declineOffer()` — offer accepted/declined (`notifyOfferAccepted`/`notifyOfferDeclined`), each reachable only once per Offer (a second response always finds `status` no longer `sent` and throws before reaching the notification call — see section 7b).
  - **No Admin-facing notifications** exist in this phase — none of the current events target an admin recipient.
- **Notification creation is synchronous and transaction-bound (Phase 7A-2).** Every `NotificationService` call above sits inside the same `DB::transaction()` closure as the business mutation it accompanies (adding one where the integration point wasn't already transactional, e.g. `Student\ApplicationController::store()`/`Organization\ApplicationController::updateStatus()`), so a Notification insert and its business action always commit or roll back together — no notification for an action that didn't actually happen, and no action silently missing its notification. An unexpected `NotificationService` failure is allowed to roll back the business transaction; this is acceptable only because notification creation is a local DB insert with no external I/O.
- **Queued transactional email is fully enabled as of Phase 7A-4.2, for seven of the eleven events** (extended to an eighth, quiz result available, in Phase 10A.2 — see below). The rule flagged above — "an external mail-send failure must never roll back or block a real business action" — is addressed by a dedicated mechanism rather than by weakening the Notification-row guarantee above: `App\Services\EmailService` (constructor-injected into `NotificationService`) queues the matching Mailable via `Mail::to($recipient->email)->queue(...)`, called from inside `NotificationService`'s own convenience method for each enabled event. Every workflow Mailable extends `App\Mail\QueuedTransactionalMail`, which implements `Illuminate\Contracts\Queue\ShouldQueueAfterCommit` — Laravel defers the actual queue push until the enclosing `DB::transaction()` genuinely commits, and simply never pushes it at all if that transaction rolls back (confirmed directly against the installed framework source, not assumed — see `QueuedTransactionalMail`'s own doc comment). `config('queue.connections.database.after_commit')` stays `false` (the project-wide default, deliberately untouched) — this is a **per-Mailable** opt-in, not a global behavior change. Queued on the `emails` queue, `tries=3`, `timeout=60s`, `backoff=[30s, 300s, 1800s]`. **No live SMTP delivery is configured** — `MAIL_MAILER` stays `log` in development; a queue worker (`php artisan queue:work`) is required to process any queued email at all, delivered or merely logged; real SMTP configuration/testing is Phase 7A-4.3.
- **Final transactional-email eligibility matrix (Phase 7A-4.2):**
  - **Email enabled — student-facing**: application rejected (`notifyApplicationRejected` → `ApplicationRejectedMail`), interview scheduled (`notifyInterviewScheduled` → `InterviewScheduledMail`), interview rescheduled (`notifyInterviewRescheduled` → `InterviewRescheduledMail`), quiz available (`notifyQuizPublished` → `QuizAvailableMail`), offer received (`notifyOfferSent` → `OfferReceivedMail`, the Phase 7A-4.1 pilot), and, **as of Phase 10A.2**, quiz result available (`notifyQuizResultAvailable` → `QuizResultMail`) — reversed from its original Phase 7A-4.2 in-app-only classification (see below) once the result-release mechanism made this event meaningfully rarer and more time-relevant than at submit time: it now fires once, only at the moment a result is actually released (immediately, on schedule, or manually — never at submit time for a deferred release), which is exactly the kind of "something changed, come look" moment the other enabled events already cover. Each enabled event is either time-sensitive/action-required (interview, quiz available, quiz result) or high enough value/low enough frequency per user (offer, rejection) to justify an email without becoming spam.
  - **Email enabled — organization-facing**: offer accepted (`notifyOfferAccepted` → `OfferAcceptedMail`), offer declined (`notifyOfferDeclined` → `OfferDeclinedMail`). Both are low-frequency, high-value terminal events an organization needs to act on promptly.
  - **In-app only — deliberately no email**: application shortlisted (`notifyApplicationShortlisted`) — not independently actionable, the student still just waits; new application (`notifyApplicationSubmitted`) — by far the highest-frequency organization-facing event (fires per applicant), emailing every one would be spam; quiz completed (`notifyQuizCompleted`) — same frequency argument, organizations review completions in batches, not one-by-one.
  - **Admin**: none — no event in this phase's matrix targets an admin recipient, in-app or email.
  - Signature note: three convenience methods needed one additional parameter to safely build their email content — `notifyInterviewScheduled()`/`notifyInterviewRescheduled()` now also take the `Interview` model (its scheduling fields only: `interview_type`, `scheduled_at`, `duration_minutes`, `meeting_link`, `location`, `interviewer_name` — never `interviewer_email`/`rating`/`decision`/`notes`/`company_feedback`), and `notifyQuizPublished()` now also takes the `Quiz` model (`passing_score`/`time_limit_minutes` only, both already student-visible — see docs/API.md's "Student-visible Quiz fields" note — never question/answer/score data). The other four newly-enabled methods (`notifyApplicationRejected`, `notifyOfferAccepted`, `notifyOfferDeclined`, plus the already-Phase-7A-4.1 `notifyOfferSent`) already received everything their email needs from their existing arguments.
- **Invitation events (Phase 8B-3, extended Phase 8B-3.1)**: `notifyInvitationReceived()` (student-facing, invitation sent), `notifyInvitationAccepted()`/`notifyInvitationDeclined()` (organization-facing, on the student's response) — all three use the existing `opportunity` notification type (no migration needed). **`notifyInvitationReceived()` now also queues an email as of Phase 8B-3.1** (`InvitationReceivedMail`, "You have been invited to apply") — the student otherwise has no reason to open the app and discover an invitation exists. `notifyInvitationAccepted()`/`notifyInvitationDeclined()` remain **in-app only, deliberately no email** — each fires too infrequently per organization to justify one, and the organization is already actively watching its own sent invitations.

## 9. AI Matching Rules

- AI matching starts simple and explainable.
- Matching score should be between 0 and 100.
- **Matching weights (v2.0, "Candidate Opportunity Preferences + Final Recommendation Match Formula" — final, product-approved, not to be altered without a new explicit product decision):**
  - **On-site / Hybrid**: Required Skills 60%, Major (academic compatibility) 25%, Location 15%.
  - **Remote**: Required Skills 70%, Major (academic compatibility) 30%, Location **not considered** — never computed, never part of the denominator, never displayed as a phantom `0`.
  - **Experience is removed from this formula entirely** (previously 20% in v1.1–v1.3). `opportunities.experience_level` is left in the database untouched for backward compatibility, but is never read by `MatchingService` any more, never excludes a candidate, and never appears in `match_breakdown`.
  - There is no education/work-mode factor either — `student_profiles` has no structured field for the former, and work mode only ever selects *which* weight table applies (above), never itself a scored factor.
  - **Missing-data rescaling** (unchanged mechanism, now applied per work-mode weight table): a factor is only included in the weighted average when its required input actually exists. If it doesn't, that factor's nominal weight is proportionally redistributed across whichever factors ARE scoreable for that candidate. If literally nothing is scoreable, the overall score is a genuine, calculated `0.00` (not null).
  - **Skills (60%/70%)**: unchanged mechanics — required skills count double, preferred skills count once, `score = matched_weight / total_weight * 100`. If the opportunity has zero required/preferred skills defined at all, skills is unavailable (redistributed), not a fake "100, trivially satisfied".
  - **Major / academic compatibility (25%/30%, `MatchingService::analyzeMajor()`)**: compares `studentProfile.major` against the Opportunity's **canonical** `eligibleMajorRecords` (section 5b) — never the legacy free-text `opportunity.field_of_study`, which remains unused by every factor. If the Opportunity has no Eligible Majors configured at all (rule B, unrestricted), this factor is unavailable (`null`, weight redistributes). If configured (rule A) and the Student's major normalize-matches one of them, this factor scores `100`; a blank major, or one that matches none of them, scores a real `0` (reachable in practice only for a stale Application Match Analysis recalculated after the Student's major changed post-submission — every Recommended Candidates row and every new Application already passed the identical comparison as the eligibility gate below).
  - **Location (15% On-site/Hybrid only, `MatchingService::analyzeLocation()`, new in v2.0)**: compares the Opportunity's canonical `location_id` against the Student's own `availableLocations` — canonical Location Catalog IDs only, never raw string equality. Never computed at all for Remote (excluded from the formula entirely, not scored as `0` and not redistributed into). For On-site/Hybrid: if the Opportunity has no `location_id` configured, this factor is unavailable (`null`, weight redistributes) — mirroring `isLocationEligible()`'s identical "unrestricted" treatment of the same case. If configured, `100` when the Student's `availableLocations` includes it (every candidate reaching this method through the normal Recommended-Candidates path is in this branch, since `isLocationEligible()` already required the identical match as a pre-scoring gate), `0` when it doesn't (defensive-only through Recommended Candidates; reachable for a stale Application Match Analysis, since Direct Apply is never gated on location eligibility).
  - **Why Major is a genuine scoring factor despite also being a gate ("Recommendation Match: Major Must Contribute to Total Score", carried into v2.0)**: `OpportunityEligibilityService::isStudentEligible()`/`isLocationEligible()` gate *whether a candidate is scored/shown at all*, computed independently of and before `MatchingService`; a candidate who fails either gate is excluded outright, never shown with a docked score. `analyzeMajor()`/`analyzeLocation()` perform the identical comparisons as genuine, separately-computed *scoring* factors — for a candidate reached through the normal path, gate and score agree by design. This is a deliberate exception to "never double-count a gate": the percentage labeled "Match" must represent **total** candidate compatibility (of which academic fit and, where relevant, location fit are genuine pillars), not a fact that disappears from the number the moment it passes a gate. `field_of_study` remains completely unused by any factor — this reasoning applies only to the real, canonical `eligibleMajorRecords`/`availableLocations` data the gates themselves already use.
  - **Points, not raw percentages, in the client-facing breakdown**: every backend response includes, per factor, the real weight (`*_weight`) and the real already-weighted contribution (`*_contribution`) in the same points that sum to `overall_match_score` — a client never multiplies a raw factor score by a weight itself, it only ever displays the numbers this service already computed. `overall_match_score` is literally defined as the sum of these already-rounded per-factor contributions (not an independently-rounded weighted average), so a "Why this match?" breakdown can never show numbers that fail to add up to the displayed total.
  - `opportunities.field_of_study` itself is **not dropped** — the column, and every historical Opportunity's stored value, remain intact for backward compatibility (see section 4/5b). It is simply never read by `MatchingService`, `OpportunityEligibilityService`, or any matching/ranking code path any more, and is treated as legacy/deprecated metadata (see the `@deprecated` note on `Opportunity::$fillable`).
- **`match_breakdown` (Matching Formula Audit, tightened by the Opportunity Academic Matching Cleanup, extended by "Recommendation Match: Major Must Contribute to Total Score" and again by "Candidate Opportunity Preferences + Final Recommendation Match Formula") makes "why this score?" answerable from real data, never a fabricated or AI-generated explanation, and always reconciles with the reported total.** Returned per candidate on Recommended Candidates (docs/API.md section 5a), it re-labels the exact scores above (`academic_match`/`major_match_score`/`major_weight`/`major_contribution`; the real required-skill counts/names plus `skills_match_score`/`skills_weight`/`skills_contribution`; `location_eligibility`/`location_match_score`/`location_weight`/`location_contribution`, section 5c) plus `major_eligibility` (always `eligible` here — the gate, distinct from `academic_match`, see above). There is no `experience_match`/`experience_match_score` key any more (Experience removed from the formula) and no `major_field_match`/`field_match_score` key — Field of Study and Experience are never part of this explanation. No new comparison or weight is introduced by this object beyond what `MatchingService::score()` itself already computed.
- **Opportunity Type interest is a pre-scoring eligibility filter for Recommended Candidates only, contributing zero score points (Candidate Opportunity Preferences patch).** `StudentProfile.interested_in` — a JSON array of canonical Opportunity Type values (`App\Support\OpportunityType::ALL`, the exact same vocabulary `Opportunity.opportunity_type` uses) — is compared against the Opportunity's own `opportunity_type` via `OpportunityEligibilityService::isTypeInterestEligible()`, checked alongside (and before) the Major/Location gates in `OpportunityRecommendationController`. A Student not interested in an Opportunity's exact type is excluded from that Opportunity's Recommended Candidates entirely, never shown with a docked score, and this preference never appears anywhere in `match_breakdown`. A Student with no `interested_in` recorded at all (`null` or `[]` — every profile created before this patch) is treated as unrestricted, mirroring every other "nothing configured" rule in `OpportunityEligibilityService`. This filter is Recommendation-only, exactly like `isLocationEligible()` — it never gates direct Apply or Invitation creation, and never changes those endpoints' existing rules.
- The system should store the final score in applications.match_score.
- The first version should use rule-based matching before external AI APIs.
- **`match_score` is calculated automatically and synchronously when a student applies (Phase 8A-2).** `Student\ApplicationController::store()` calls `MatchingService::analyze()` and persists the result inside the same `DB::transaction()` as the Application insert, before the "New Application" notification is created — deterministic, no external I/O, no queue, no new endpoint. Existing applications created before this phase are **not backfilled**; they keep a `null` match_score until an organization explicitly recalculates via `POST .../analyze`.
- **`POST .../analyze` remains the manual recalculation endpoint**, using the same `MatchingService` formula (no duplicate implementation) — it always recomputes and overwrites the stored score, whether or not one already exists (e.g. after the student or opportunity data changes).
- **`match_score` is organization-internal and must never be exposed to the student it belongs to (Phase 8A-1).** A student has no product reason to see how they were scored, and exposing it would also leak whether/how they were ranked against other applicants. Enforced per-response on every Student-facing endpoint that returns an `Application` (directly or nested under Interview/Assessment) via `App\Http\Controllers\Student\Concerns\HidesInternalApplicationFields` — see docs/API.md section 5. This is a field-level rule, not a null-only omission: an application with a real calculated score (including `0`, a legitimate low score) must be hidden exactly the same as one that hasn't been scored yet. This still holds now that scores are calculated automatically on apply.
- **Organization applicant lists are ranked by `match_score` (Phase 8A-1).** `GET /organization/applications` and `GET /organization/opportunities/{opportunity}/applications` order applicants by `match_score` descending, with not-yet-calculated (`null`) scores always last regardless of any calculated value, and `applied_at` ascending as the tie-breaker. Ranking only ever reads the already-stored score — it never triggers a calculation, and it never reorders any Student-facing list.
- **AI CV Skill Extraction (Phase 8A-6) is a separate, suggestion-only feature and never touches `match_score` or `MatchingService`.** `AiSkillExtractionService` (the first external-AI integration in this project) reads only a CV's already-extracted `parsed_text` and returns skill name/confidence suggestions — it never computes, requests, or influences a match score, ranking, or hire/no-hire signal of any kind. The rule-based `MatchingService` formula above remains the sole, unmodified, authoritative source of `match_score` for every application, exactly as before this phase.
- **AI skill suggestions require explicit Student approval before becoming real data.** The extraction endpoint (`POST /student/cvs/{cv}/extract-skills`) never writes to `student_skills`, `skills`, or `cvs` — it only returns transient, unpersisted suggestions. A suggestion becomes a real `StudentSkill` row only when the Student explicitly selects it and the existing `POST /student/skills` endpoint is called, exactly the same endpoint and validation path used for a manually-added skill. Nothing about this feature bypasses or duplicates that endpoint.
- **Only existing Admin-owned `Skill` catalog entries can be accepted from an AI suggestion.** A suggested skill name that doesn't match an existing `skills` row (case-insensitive exact match) is returned as unmatched (`skill_id: null, is_available: false`) and cannot be selected for adding — the AI extraction flow never creates a new `Skill` record. The Admin-managed catalog (section 3/Admin Skill Rules) remains the sole owner of what skills exist in the system.
- **Minimum-data principle for the AI request.** The only data sent to the AI provider is the CV's `parsed_text`. The student's name, email, phone number, exact user ID, password, auth tokens, `match_score`, offers, application status, and interview/company feedback are never included in the outbound AI request — enforced by `AiSkillExtractionService` and covered by an explicit automated test asserting none of that data appears in the request payload. `parsed_text` itself continues to never be returned in any API response (Phase 8A-5) and is not included in the extraction endpoint's response either.
- **An AI provider failure never damages CV, Profile, or Application data.** A missing API key, a provider timeout/error, or a malformed AI response always fails safely (a controlled `503`) and leaves every table byte-for-byte unchanged — extraction is a pure read of `parsed_text` with no side effects of its own on any table.

## 9a. Skill Catalog & Skill Evidence Rules (Phase 8A-6.1)

- **The Skill Catalog is Admin-curated and is now initialized with a baseline seeder.** `database/seeders/BaselineSkillSeeder` populates a realistic starter catalog spanning Civil Engineering, Architecture, Computer/Software Engineering, Electrical/Electronics Engineering, Mechanical Engineering, Business, and Healthcare, using `Skill::firstOrCreate` on `name` — it is deterministic, idempotent (safe to run any number of times), and never overwrites or deletes an existing Skill row (manually created or previously seeded). This is a one-time bootstrap of realistic starting data, not a replacement for Admin ownership of the catalog — Admin can still create, rename, or delete any Skill exactly as before.
- **An AI-extracted skill with no catalog match now becomes a pending catalog suggestion instead of a dead end.** When `AiSkillExtractionService` cannot match a suggested name to an existing `Skill` (Phase 8A-6's exact-match rule, now normalized — see below), it creates (or reuses) a `skill_suggestions` row with `source = ai_cv` and `status = pending`, and returns `suggestion_id`/`suggestion_status` alongside the existing unmatched-suggestion shape. The AI still never creates a `Skill` row directly, and still never approves its own suggestion — only an Admin can turn a suggestion into a real catalog entry.
- **Skill name normalization (trim, lowercase, collapse whitespace) is applied consistently everywhere a skill name is compared:** AI-to-catalog matching, pending-suggestion deduplication, and Admin approval's duplicate check (`App\Support\SkillNameNormalizer`). This intentionally stays a simple, deterministic rule — no fuzzy/NLP matching — so "AutoCAD", "autocad", and "AUTOCAD" always collapse to the same entry, without over-matching unrelated names.
- **Repeated extraction of the same unmatched name reuses the same pending suggestion — it never creates duplicates.** Suggestion lookup is scoped to `(normalized_name, status = pending)`, so multiple students (or repeated Analyze CV calls by the same student) all resolve to one shared pending row. A name that was previously rejected can be freshly re-suggested later, since a rejected row no longer matches the "pending" lookup — this is intentional, not a bug.
- **Only an Admin can approve or reject a pending Skill suggestion**, via `PUT /admin/skill-suggestions/{id}/approve` or `.../reject` (`Admin\SkillSuggestionController`, admin-role-gated). Approving creates a real `Skill` from the suggestion's name — or, if an equivalent Skill (by normalized name) already exists by the time of approval (e.g. the baseline seeder or another Admin action created it in the meantime), reuses that existing Skill instead of creating a duplicate. Rejecting a suggestion never creates a Skill. A suggestion that has already been approved or rejected cannot be re-reviewed — the endpoint returns a controlled `409` rather than silently double-processing it or undoing the earlier decision.
- **Every `StudentSkill` now records its evidence source: `manual` (self-declared by the student) or `cv_ai` (accepted from an AI CV suggestion).** The column defaults to `manual`, so every `StudentSkill` row created before this phase is automatically and correctly classified as manual with no backfill step required. A student adding a skill through the ordinary manual flow always gets `source = manual`; a student accepting an AI CV suggestion always gets `source = cv_ai`.
- **A real, end-to-end manual Add Skill flow (Phase 8A-6.3) reuses `POST /student/skills` unchanged — no new create endpoint was needed.** The only genuinely missing piece was a way for a student to discover a valid `skill_id` to submit: `GET /student/skills/catalog` (new) returns the full Skill catalog for this purpose. It carries no write capability of its own and enforces no additional rule beyond ordinary authentication — every duplicate/evidence/spoofing rule below still applies exactly as it did before this endpoint existed.
- **`source = cv_ai` cannot be spoofed by the client.** `POST /student/skills` never trusts a client-supplied `cv_ai` claim on its own — the backend independently verifies, via a small `cv_skill_evidence` record `(student_id, cv_id, skill_id)` written server-side whenever `AiSkillExtractionService` resolves a name to a real catalog Skill, that this exact student's own CV genuinely produced this exact skill through the AI extraction flow. A `cv_ai` claim with no matching evidence row — including a claim naming another student's CV, an arbitrary catalog skill never actually extracted from that CV, or a CV whose evidence was cascade-deleted along with the CV itself — is rejected with a `422`, and the skill is never stored with a false `cv_ai` source. The existing manual-add path is completely unaffected: no evidence is required or checked when `source` is `manual` (the default).
- **`cv_ai` ("CV-supported") is explicitly not credential verification.** It means the skill name was found in text extracted from a CV this student uploaded, and identified through the AI extraction flow — nothing more. It does not confirm actual proficiency, and it is never labeled "Verified" anywhere in the product (Student or Organization UI, or API). Certificate upload and external credential verification remain explicitly out of scope and are not implemented by this phase.
- **`MatchingService` is completely unchanged by this phase.** It continues to read `StudentSkill` rows exactly as before (`skill_id`, `years_of_experience`) and never reads or weights the `source` column — a `manual` and a `cv_ai` `StudentSkill` with otherwise-identical data produce an identical `match_score`. Evidence-aware scoring (e.g. weighting CV-supported skills more heavily) is explicitly deferred to a future phase, not implemented here.
- **Organization-visible evidence labels never leak AI internals.** When an Organization views an applicant's skills, each one is labeled `CV-supported` or `Self-declared` only — the underlying `parsed_text`, the AI provider's raw request/response, the extraction confidence score, and any suggestion metadata are never included in any Organization-facing response.
- **A CV may be renamed at any time, regardless of its default status or whether it's referenced by an Application (Phase 8A-6.2).** `PATCH /student/cvs/{cv}` changes only `title` — every other CV field, including `file_path` (the actual PDF), is untouched. An `Application.cv_id` foreign key always identifies the CV it references by id, never by title, so there is no historical-title-integrity concern renaming could violate; this is a completely different question from `DELETE`'s "used in an Application" `409` conflict (section 5, unchanged), which exists to protect the CV *record and file* from disappearing out from under an Application, not its display name.
- **AI skill extraction requires the uploaded PDF to be recognized as CV/resume-like content before skill extraction proceeds (Phase 8A-6.2).** The root problem this closes: a technical-sounding textbook chapter, lecture notes, a research article, or any other unrelated PDF can mention real programming languages/tools/technologies while teaching about them — that is not evidence the uploading student personally has those skills, and Phase 8A-6's original implementation had no defense against it (any PDF with extractable text was sent straight to skill extraction). Two gates now run inside `Student\CVController::extractSkills()`, in order, before `AiSkillExtractionService` (and therefore before any `CvSkillEvidence`/`SkillSuggestion` write) is ever reached:
  1. **A deterministic minimum-readable-text-length check.** Below a small fixed character threshold, the text is treated as "not enough to analyze" — this is a cheap pre-filter for a genuinely empty/near-empty PDF (e.g. a scanned page with a stray watermark), not a document-type judgment, and never calls the AI provider.
  2. **A bounded AI classification** (`App\Services\CvDocumentClassifierService`) — the same configured provider (Groq), HTTP pattern, and single-bounded-request-no-retry philosophy as `AiSkillExtractionService`, but a separate, narrower prompt asking only whether the text reads as one person's own CV/resume (education/experience/projects/skills/certifications/summary, organized as a personal history with associated dates) as opposed to instructional/explanatory prose written to teach a reader about a subject. **The presence of technical keywords alone is explicitly never sufficient** — the classifier is instructed to judge document-level structure and intent, not vocabulary. It does not require every section to be present, so a sparse student CV (e.g. education + projects + skills, no paid work experience yet) still classifies as a real CV.
  - A document that fails the classification gate never reaches `AiSkillExtractionService` — zero `CvSkillEvidence`, zero `SkillSuggestion`, zero `StudentSkill` rows are ever written from a rejected document, and the CV row itself is untouched (it is never deleted or flagged — the student may simply try analyzing a different, real CV, or re-upload).
  - **A classification-provider failure is never reported as "not a CV".** `CvDocumentClassifierService` throws the exact same `AiSkillExtractionException` a real extraction-provider failure throws, and `CVController` maps both to the identical safe `503` — a Groq outage during the classification call must never be shown to the student as their document being rejected.
  - This gate is presentation-agnostic backend enforcement — no amount of Flutter-side validation could substitute for it, since a client can always be bypassed by calling the API directly.

## 9b. Education Verification Rules (Phase 8B-1)

- **"Education Verified" means the platform Admin reviewed a Student's uploaded education-proof document and approved it — nothing more.** It is **not** a direct university-API check, a government verification, or a cryptographic/blockchain credential check. This phase implements none of those, and the product must never imply otherwise (no "Verified" label appears without this exact meaning behind it, and the Flutter UI/API never call it anything stronger).
- **Account creation and education verification are entirely separate.** Registering as a Student never requires, checks, or blocks on an education-verification submission. A student with `status = not_submitted` can fully use every other feature of the platform.
- **Applying to an opportunity is not gated on education verification in this phase.** `POST /opportunities/{opportunity}/apply` is completely unmodified by Phase 8B-1 — a student with no submission, a `pending` one, or even a `rejected` one can still apply exactly as before. Education verification is introduced purely as an Organization-visible **trust signal** for this phase, not an eligibility gate. Gating Apply on verification status is explicitly deferred to a future phase, and was deliberately not implemented here even though the underlying data would make it straightforward — introducing a new hard business restriction on Applying is a decision this phase does not make unilaterally.
- **One verification per student, updated in place.** `education_verifications.student_id` is unique — a rejected submission is resubmitted by updating that same row (not creating a new one), matching the "smallest safe architecture" preference for this phase.
- **A `verified` submission cannot be resubmitted/replaced in v1.** `POST /student/education-verification` returns a controlled `409` if the student's current verification is already `verified`. Only a `pending` (unusual, but harmless — replaces the pending submission with a fresh one) or `rejected` verification can be resubmitted.
- **A rejection always requires a reason**, and that reason is only ever cleared by a fresh resubmission or a subsequent approval — never silently dropped.
- **Already-reviewed submissions are never silently re-reviewed.** Both `PUT .../verify` and `PUT .../reject` return a controlled `409` ("This education verification has already been reviewed.") if the submission isn't currently `pending` — mirrors the exact pattern `Admin\SkillSuggestionController` already established for approve/reject (section 9a). An Admin action can never silently overwrite a prior Admin decision.
- **A student can never set their own review outcome.** `POST /student/education-verification` never reads `status`, `reviewed_at`, or `reviewed_by_admin_id` from the request body at all — every submission (first or resubmitted) is unconditionally forced to `status = pending` with review metadata cleared, regardless of what the client sends.
- **The document itself is never publicly reachable.** Stored under private Laravel storage (`storage/app/private/education-verifications/{student_id}/...`, the `local` disk, mirroring CV storage), reachable only through the ownership-checked `GET /student/education-verification/document` (the student's own) or the Admin-only `GET /admin/education-verifications/{id}/document` — never a direct/guessable URL, and the raw `document_path` is never included in any JSON response to any role.
- **Organization visibility is status-only.** An Organization reviewing an applicant sees `education_verification_status` (`not_submitted`/`pending`/`verified`/`rejected`) and nothing else — institution name, degree/program, rejection reason, submission/review dates, and the reviewing admin's identity are all Admin/Student-only and never appear in any Organization-facing response. There is no product reason identified for exposing the rejection reason to an Organization, so it stays withheld.
- **No OCR, no AI/automatic document-authenticity detection, no external credential-verification provider, no blockchain.** The entire review is a human Admin looking at an uploaded PDF and clicking Verify or Reject — exactly as scoped for this phase; none of these are implemented.
- **File cleanup never risks an orphan or a wrong-path delete.** The new document is always stored and the DB row safely created/updated *before* the previous managed file (on a resubmission) is deleted — and only when that previous path is one this application itself generated under the owning student's own folder, mirroring `CVController`'s exact delete-safety rule. If the DB write fails after the file was stored, the just-stored file is removed so it never becomes an orphan.

## 10. Security Rules

- Passwords must be hashed.
- Users cannot access data that does not belong to them.
- Admin-only actions must be protected.
- Organization-only actions must be protected.
- Student-only actions must be protected.
- API responses should not expose sensitive data.
